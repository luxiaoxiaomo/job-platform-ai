G1：P4 智能匹配规划与 MVP 切分
  目标：把“智能匹配”从方向变成可执行 PRD 和任务包，明确第一版到底做什么、不做什么。
  产出：P4 PRD、接口契约、数据依赖、算法/规则边界、前后端任务拆分、验收标准。
  适合原因：这是当前交接文件里的下一条主线。

  G2：空岗发布核心业务闭环验收
  目标：从企业发布岗位、求职者浏览/搜索/投递、企业查看候选人、沟通/状态流转，做一次完整端到端验收。
  产出：验收清单、缺陷列表、自动化/手工验证记录、修复任务。
  适合原因：我们做了很多模块，但需要确认它们作为“空岗发布平台”真正串起来。

  G3：匹配质量运营从看板走向调优闭环
  目标：基于现有 Match Quality P1，看低分率、分层质量、异常提示、调优建议是否能反向驱动规则调整。
  产出：调优流程、运营动作定义、规则修改建议确认机制、质量前后对比。
  适合原因：R-P4-01 已完成展示能力，但还没形成“发现问题 -&gt; 调规则 -&gt; 验效果”的闭环。

  偏工程落地

  G4：上线前技术体检
  目标：后端迁移、权限、数据一致性、错误处理、前端构建、接口契约、日志与敏感信息做一次上线前 audit。
  产出：风险清单、修复项、测试结果、上线阻断项。
  适合原因：现在功能多，提交也大，需要一次系统性收口。

  G5：基础数据与标签治理运营化
  目标：把标准职位、标签库、操作日志、公共标签接入规则变成可运营流程。
  产出：运营角色流程、标签新增/停用规则、影响范围检查、后台验收。
  适合原因：标签已经接入岗位、求职意向、简历画像和搜索，但治理规则还可以更明确。

  G6：演示环境与样例数据准备
  目标：准备一套能演示完整业务流的稳定 demo 数据和脚本。
  产出：企业、岗位、求职者、简历画像、匹配规则、投递记录、质量看板样例数据。
  适合原因：适合产品复盘、客户演示、后续测试。

  偏协作和长期资产

  G7：项目记忆与交接机制升级
  目标：把 AhaDiff、docs/HANDOFF.json、协作看板、PRD/验收记录统一成可持续交接机制。
  产出：记忆生成流程、每次提交后复盘规则、文档更新规则。
  适合原因：对多 Agent 协作很有价值，但不是业务功能本身
