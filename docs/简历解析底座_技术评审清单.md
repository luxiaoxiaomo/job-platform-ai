## 一、架构设计评审

### 1.1 表设计方案选择

#### 🎯 核心问题
**Q1：采用 STIC 大宽表（60+字段）还是 Codex 分层表（8张新表）？**

**方案对比**

| 维度 | STIC 大宽表 | Codex 分层表 |
|------|-------------|-------------|
| **实现速度** | ✅ 快（表已设计好） | ⚠️ 慢（8张表+迁移） |
| **可维护性** | ❌ 差（职责混乱） | ✅ 好（职责清晰） |
| **可追溯性** | ❌ 无法追溯历史解析 | ✅ 完整追溯链路 |
| **扩展性** | ❌ 字段堆积 | ✅ 按需扩展 |
| **数据迁移** | ✅ 无需迁移 | ⚠️ 需要迁移现有数据 |

**空岗平台经验**：
- ✅ 我们已采用**分层设计**：`users` → `seeker_resumes` → `job_applications`
- ✅ 模块拆分清晰：`user/job/application/company_certification` 各自独立
- ⚠️ 但简历模块当前只有 `seeker_resumes` 一张表（类似 STIC 大宽表）

**建议**：
- ⏰ **短期（1-2周）**：先用 STIC 大宽表快速验证 AI 解析能力
- 🎯 **中期（1个月）**：逐步重构为 Codex 分层表，避免技术债
- 📊 **理由**：简历解析是核心能力，值得投入精力做好架构

### 1.2 与现有空岗平台的集成

#### 🎯 核心问题
**Q2：简历解析底座如何与现有 `seeker_resumes` 对接？**

**当前空岗平台简历模块现状**：
```python
# backend/job-platform/app/modules/resume/models.py
class SeekerResume(Base):
    __tablename__ = "seeker_resumes"
    id = Column(Integer, primary_key=True)
    seeker_id = Column(Integer, ForeignKey("users.id"))
    file_url = Column(String(500))
    file_name = Column(String(255))
    content_type = Column(String(100))
    file_size = Column(Integer)
    parsed_snapshot = Column(Text)  # ← 当前只有这个字段存解析结果
```

**集成方案**

| 方案 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **方案A：平行共存** | 保留 `seeker_resumes`，新建 8 张底座表 | 不破坏现有功能 | 数据冗余、同步复杂 |
| **方案B：废弃重建** | 废弃 `seeker_resumes`，全用底座表 | 架构清晰 | 影响现有代码 |
| **方案C：渐进迁移** | 先新增底座表，旧表加外键指向新表 | 平滑过渡 | 过渡期维护成本高 |

**空岗平台经验**：
- ✅ 我们已有 `seeker_resumes`（6月14日新增）
- ✅ 前端已有简历上传页 `SeekerResumeUpload.jsx`
- ⚠️ 但 `parsed_snapshot` 字段当前存的是临时文案（会乱码）

**建议**：
- 🎯 **采用方案C（渐进迁移）**
- 📝 步骤：
  1. 新增 `resume_uploads`, `resume_parse_runs`, `resume_extracted_texts`, `resume_chunks`（P1）
  2. `seeker_resumes` 加字段：`current_upload_id`, `current_parse_run_id`
  3. 前端上传接口返回：`{resume, upload, parse_run}`
  4. 逐步把 `parsed_snapshot` 废弃，改读 `resume_structured_profiles`

## 三、技术选型评审

### 3.1 向量化模型选择

#### 🎯 核心问题
**Q5：简历和岗位向量化用什么模型？**

**候选方案**

| 方案 | 模型 | 优点 | 缺点 | 成本 |
|------|------|------|------|------|
| **A：通义千问 Embedding** | `text-embedding-v3` | 中文效果好、官方支持 | 依赖阿里云 | ¥0.0007/千token |
| **B：OpenAI Embedding** | `text-embedding-3-large` | 效果好、生态成熟 | 国内访问慢 | $0.13/百万token |
| **C：开源模型** | `bge-large-zh-v1.5` | 可本地部署、免费 | 需要GPU、维护成本 | GPU费用 |
| **D：sentence-transformers** | `paraphrase-multilingual` | 轻量、易部署 | 中文效果一般 | 免费 |

**空岗平台经验**：
- ⚠️ 我们还没接入向量化（pgvector 已部署但未使用）
- ✅ 后端已集成通义千问 API（用于岗位 AI 代写）

**V1.3 需求明确提到**：
- "通过 BERT 编码为向量"
- "语义相似度计算"

**建议**：
- 🎯 **短期（P1-P2）**：用通义千问 Embedding（已有 API key，快速验证）
- 🎯 **中期（P3-P4）**：评估开源 `bge-large-zh-v1.5`（成本更低）

### 4.3 异步任务设计

#### 🎯 核心问题
**Q9：解析任务是同步还是异步？如何实现？**

**Codex 设计说明**：
- "第一阶段可以同步执行简单解析，后续再切换为 Celery 异步任务"
- "接口和表设计按异步状态设计，避免后续推翻"

**候选方案**

| 方案 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **同步执行** | 简单 docx 解析（<5秒） | 实现简单、无需队列 | 阻塞请求、不适合 PDF OCR |
| **后台线程** | 中等复杂度（<30秒） | 实现简单、无需 Celery | 无法分布式、不适合大批量 |
| **Celery 异步** | 复杂解析、批量上传 | 可分布式、可监控 | 需要 Redis/RabbitMQ、增加复杂度 |

**空岗平台经验**：
- ✅ 我们已部署 Redis（用于缓存）
- ❌ 我们还没用 Celery（当前所有任务都是同步）
- ⚠️ 企业认证 OCR 是同步调用（<3秒），没遇到性能问题

**建议**：
- 🎯 **P1-P2 阶段**：用**后台线程**（Python `threading` 或 FastAPI `BackgroundTasks`）
- 🎯 **P3-P4 阶段**：批量上传、OCR 场景切换为 **Celery**
- 📊 **理由**：先验证功能，再优化性能

## 八、补充评审（用户发现的问题）

### 8.1 明细表设计缺失

#### 🎯 核心问题
**Q13：Codex 设计缺失了简历明细表，如何做简历筛选？**（用户提出）

**问题描述**

Codex 当前设计只有 `resume_structured_profiles` 存 JSON 字段：
```json
{
  "education_json": [...],
  "work_json": [...],
  "skills_json": [...]
}
```

**但缺失了明细表**（STIC 原始设计有）：
- `resume_educations` - 教育经历明细
- `resume_work_experiences` - 工作经历明细
- `resume_projects` - 项目经历明细
- `resume_skills` - 技能明细
- `resume_certificates` - 证书明细
- `resume_languages` - 语言能力明细

**为什么需要明细表？**

| 场景 | JSON字段（Codex设计） | 明细表 |
|------|---------------------|--------|
| 筛选"有阿里工作经历" | ❌ `WHERE work_json::text LIKE '%阿里%'` 慢、无索引 | ✅ `JOIN work_experiences WHERE company='阿里'` |
| 统计学历分布 | ❌ 复杂、性能差 | ✅ `GROUP BY edu_degree` 快速 |
| 技能精确匹配 | ❌ JSON 数组难精确匹配 | ✅ `JOIN skills WHERE skill_name IN (...)` |
| 人岗匹配算法 | ❌ 需解析 JSON | ✅ 直接 JOIN 关联表 |

**Codex 技术设计第289行的说明**：
> "结构化 JSON 和明细表不是二选一，最终都需要。"  
> "P2: resume_structured_profiles（JSON）+ 核心规范化明细表"

**但他没写具体明细表设计** ⚠️

**建议**：
- 🎯 **P2 阶段必须补充 6 张明细表**：educations, work_experiences, projects, skills, certificates, languages
- 📝 **数据流**：解析结果 → `resume_structured_profiles` (JSON) → 确认后拆分存入明细表
- ✅ **双轨存储**：JSON 保留（灵活、迭代快），明细表用于业务查询（性能、筛选）

**修正后的完整表清单（14张）**：
- Codex 原有 8 张底座表
- 新增 6 张明细表（简历筛选必需）
