# R-P3-04 规则配置落库与只读管理页协作计划

## 背景

R-P3-03 已经把匹配权重、贡献分和解释字段从接口层打通。当前默认规则配置仍然在后端代码里，这能支撑页面展示，但还不是真正的“可管理规则”。

R-P3-04 的目标是把规则配置落到数据库，并在管理端提供只读入口。这样后续 R-P3-05 做编辑、R-P3-06 做多模板和版本对比时，不需要再推翻表结构。

## 本轮目标

R-P3-04 交付三件事：

1. 后端新增规则配置表和维度表。
2. 匹配服务优先从数据库读取规则，查不到时 fallback 到代码默认配置。
3. 管理端提供规则列表和详情只读页，能看到当前规则、维度、权重、状态和版本信息。

本轮不做编辑保存，不做 AB 测试，不做 Redis 缓存。

## 后端分工，Codex 负责

### 数据表

新增 `match_rule_configs`：

```text
id
name
strategy
scope
status
version
description
parent_version_id
effective_from
effective_to
created_by
updated_by
created_at
updated_at
```

字段说明：

- `scope`：规则应用范围。默认 `global`，后续可扩展为 `job_category:tech`、`job_category:sales`、`recruiter_id:123`、`job_id:123`。
- `status`：`draft`、`active`、`testing`、`archived`。R-P3-04 查询默认只使用 `active`。
- `version`：规则版本号。
- `parent_version_id`：上一版本，用于后续回滚和版本链路。
- `effective_from` / `effective_to`：生效窗口，R-P3-04 只预留字段，不做定时切换。
- `created_by` / `updated_by`：操作人，先记录用户 ID，后续审计用。

新增 `match_rule_dimensions`：

```text
id
config_id
dimension_key
label
weight
enabled
description
scoring_method
logic_json
sort_order
created_at
updated_at
```

字段说明：

- `weight`：配置权重。
- `enabled`：维度是否启用。
- `logic_json`：结构化规则预留，例如：

```json
{
  "type": "keyword_match",
  "boost": 1.2,
  "required_keywords": ["Python", "SQL"],
  "optional_keywords": ["React"]
}
```

R-P3-04 只读取和展示 `logic_json`，不做可视化编辑。

### 默认数据

migration 或启动种子要写入一套默认规则：

```text
name: 默认人岗匹配规则 V1
strategy: rule_v1
scope: global
status: active
version: 1
```

默认维度：

| key | label | weight | enabled |
| --- | --- | --- | --- |
| skill | 技能匹配 | 35 | true |
| experience | 经验年限 | 20 | true |
| education | 学历匹配 | 15 | true |
| city | 城市匹配 | 10 | true |
| salary | 薪资匹配 | 10 | true |
| intention | 岗位意向 | 10 | true |

### 查询逻辑

规则选择优先级：

1. 如果传 `job_id`，后续可根据岗位类型、招聘者、岗位 ID 找最匹配规则。R-P3-04 可以先降级到 `global`。
2. 如果传 `scope`，查询该 scope 的 active 规则。
3. 如果没有传参，查询 `global` 的 active 规则。
4. 如果数据库没有可用规则，fallback 到代码默认配置。

动态归一化沿用 R-P3-03：

```text
configured_total = sum(enabled dimensions weight)
effective_weight = weight / configured_total * 100
weighted_score = dimension_score * effective_weight / 100
overall_score = round(sum(weighted_score))
```

如果启用维度权重总和为 0，应跳过该 DB 配置并 fallback 到代码默认配置，或返回明确配置错误。R-P3-04 建议 fallback，保证匹配功能可用。

### 后端接口

管理端查询接口：

```http
GET /api/v1/matches/rule-configs?scope=global
GET /api/v1/matches/rule-configs?job_id=123
GET /api/v1/matches/rule-configs/{id}
GET /api/v1/matches/rule-configs/{id}/history
```

保留兼容接口：

```http
GET /api/v1/matches/rule-configs/default
```

建议响应结构复用 R-P3-03 的 `MatchRuleConfigResponse`：

```json
{
  "id": 1,
  "name": "默认人岗匹配规则 V1",
  "strategy": "rule_v1",
  "scope": "global",
  "status": "active",
  "version": 1,
  "description": "规则版 V1",
  "configured_total_weight": 100,
  "effective_total_weight": 100,
  "dimensions": [
    {
      "key": "skill",
      "label": "技能匹配",
      "weight": 35,
      "configured_weight": 35,
      "effective_weight": 35,
      "enabled": true,
      "description": "岗位标签、岗位描述中的技能要求与简历技能做规则匹配",
      "scoring_method": "命中岗位技能越多，分数越高；未识别岗位技能时按中性分处理",
      "logic": {
        "type": "keyword_match"
      },
      "sort_order": 1
    }
  ],
  "updated_at": "2026-06-17T00:00:00"
}
```

`GET /history` 本轮可以先返回当前规则的版本链。如果没有历史，返回只包含当前版本的数组，或者空数组加当前版本字段。不要为了 history 做复杂回滚逻辑。

### 权限

R-P3-04 先用现有 admin 权限或管理端鉴权能力。暂不做复杂权限体系。

查询接口建议：

- 管理端规则列表和详情：admin 可访问。
- 匹配计算读取规则：内部 service 使用，不额外暴露给普通用户编辑。
- `rule-configs/default` 如果当前前端只读展示需要，可允许 seeker 查询；如果管理端使用，则改为 admin。需要按现有前端调用场景确认。

### 后端验收

- migration 可执行。
- 默认规则数据可查询。
- 匹配接口从 DB 配置读取权重。
- 删除或缺失 DB 配置时，匹配接口 fallback 到代码默认配置。
- 动态归一化测试通过。
- `GET /rule-configs`、`GET /rule-configs/default`、`GET /rule-configs/{id}` 测试通过。
- 现有 matches/jobs/resumes 测试不回归。

## 前端分工，Claude Code 负责

### 页面范围

管理端新增只读页面：

```text
/admin/basic-data
/admin/match-rules/:id
```

预留但不实现：

```text
/admin/match-rules/:id/edit
/admin/match-rules/:id/history
```

Claude Code 确认的落点：

- 规则列表先放在“基础数据”页面内作为子模块，不单独新增一级菜单。
- 点击规则后进入独立详情页 `/admin/match-rules/:id`。
- 编辑按钮置灰，并用 tooltip 提示“后续开放”。
- history 入口本轮隐藏，不做置灰入口。
- `logic_json` 在详情页折叠展示。
- 鉴权沿用现有 admin 机制。

### 规则列表页

展示字段：

- 规则名称
- scope
- status
- version
- 维度数量

- 更新时间

交互：

- 点击进入详情页。
- 编辑按钮置灰，并提示“后续开放”。
- history 入口隐藏。

### 规则详情页

展示规则基础信息：

- name
- strategy
- scope
- status
- version
- description
- effective_from / effective_to
- updated_at

展示维度列表：

- label
- dimension_key
- enabled
- configured_weight
- effective_weight
- description
- scoring_method
- logic_json 简要展示
- `logic_json` 默认折叠，展开后显示格式化 JSON 或只读摘要。

页面必须按后端返回的 `dimensions` 动态渲染，不写死六个维度。

### 前端验收

- `npm.cmd run build` 通过。
- 规则列表能展示默认规则。
- 规则详情能展示维度和权重。
- 没有规则时显示空状态或 fallback 提示。
- 编辑入口不误导用户，不允许提交。

## 不做范围

R-P3-04 不做：

- 编辑权重。
- 启停维度。
- 保存新版本。
- 版本回滚。
- 定时切换规则。
- 多 scope 自动匹配。
- AB 测试分流。
- Redis 缓存。
- LLM 生成规则。

这些放到 R-P3-05 和 R-P3-06。

## 协作顺序

1. Codex 做 migration、model、repository、service、schema、API。
2. Codex 补默认规则数据和 fallback。
3. Codex 跑后端测试并更新看板。
4. Claude Code 做管理端列表页和详情页。
5. Claude Code 跑前端 build。
6. 双方联调默认规则查询和页面展示。
7. 通过后看板标记 R-P3-04 Done。

## 建议结论

R-P3-04 要把底座做扎实，但不要提前做完整规则后台。表结构和接口要为版本、scope、logic_json 留位置；前端先只读展示。这样 R-P3-05 做编辑时，只是在已有结构上加写操作，而不是重新设计。
