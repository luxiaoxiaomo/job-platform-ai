### ⚠️ 其他发现的遗漏

#### 2.2 岗位JD解析表

**STIC 表**：`hhr_ta_position_recognition` - 岗位信息解析表

**用途**：
- 岗位JD的结构化解析结果
- 岗位标签、关键词
- 岗位向量（jd_vector）

**Codex 设计**：❌ **没有明确**

**当前空岗平台**：
- `jobs` 表只有原始 JD 字段（`requirements`, `responsibilities`）
- 没有岗位解析结果存储

**建议**：
- 🎯 **新增 `job_parsed_profiles` 表**（对应简历的 `resume_structured_profiles`）

```sql
CREATE TABLE job_parsed_profiles (
  id BIGINT PRIMARY KEY,
  job_id BIGINT NOT NULL,  -- 关联 jobs.id
  parse_version VARCHAR(50),  -- 解析版本
  requirements_json JSON,  -- 结构化要求
  responsibilities_json JSON,  -- 结构化职责
  jd_vector BLOB,  -- JD向量（embedding）
  tags_json JSON,  -- 岗位标签（8维度）
  keywords_json JSON,  -- 岗位关键词（6维度）
  created_at DATETIME,
  FOREIGN KEY (job_id) REFERENCES jobs(id)
);
```

## 四、非功能性遗漏

### 4.1 数据隐私与安全

#### 敏感字段加密

**STIC 表包含敏感字段**：
- `phone` - 联系电话
- `email` - 联系邮箱
- `id_card` - 身份证号

**Codex 设计**：❌ 没提到加密

**建议**：
- 🔴 **P1 阶段考虑**：敏感字段加密存储
- 选项A：数据库层加密（MySQL Encryption）
- 选项B：应用层加密（Python `cryptography`）
- ✅ 参考空岗平台：我们已有 `seeker_profiles.phone` 存储，未加密（但生产需加密）

---

### 4.2 数据脱敏

**场景**：管理员查看简历列表时

**STIC 设计**：❌ 没提到

**建议**：
- 📝 API 返回时自动脱敏：
  - `phone`: `138****5678`
  - `email`: `wan***@gmail.com`
  - `id_card`: `3301**********1234`

---

### 4.3 软删除 vs 硬删除

**Codex 设计**：所有表都是物理删除（DELETE）

**建议**：
- 🎯 **简历相关表建议软删除**（加 `deleted_at` 字段）
- 理由：
  - 简历是核心资产，误删风险高
  - 法律合规（保留删除记录）
  - 可恢复

---

### 4.4 审计日志

**Codex 设计**：
- ✅ 有 `resume_profile_change_logs`（回写日志）
- ❌ 没有通用审计日志

**建议**：
- 🟡 **P3 阶段考虑**：新增 `audit_logs` 表
- 记录：谁、何时、对哪条简历、做了什么操作（查看/下载/编辑/删除）

## 五、性能与扩展性遗漏

### 5.1 向量索引

**Codex 设计**：
- ✅ `resume_chunks` 表有 `vector_ref` 字段
- ❌ 但没说明向量索引类型

**pgvector 索引选项**：
```sql
-- 选项A：IVFFlat（适合中等数据量）
CREATE INDEX ON resume_chunks USING ivfflat (embedding vector_cosine_ops);

-- 选项B：HNSW（适合大数据量，更快）
CREATE INDEX ON resume_chunks USING hnsw (embedding vector_cosine_ops);
```

**建议**：
- 📝 P4 阶段需明确向量索引方案

---

### 5.2 分区表

**场景**：简历数据量大（>100万）时

**建议**：
- 🟡 **按时间分区**：`resume_uploads` 按 `created_at` 月度分区
- 🟡 **按状态分区**：`resume_parse_runs` 按 `status` 分区（pending/running/succeeded/failed）

---

### 5.3 归档策略

**场景**：历史简历数据

**STIC/Codex 设计**：❌ 都没提到

**建议**：
- 📝 **归档规则**：超过 2 年未更新的简历 → 归档表
- 📝 **冷热分离**：归档表用廉价存储
