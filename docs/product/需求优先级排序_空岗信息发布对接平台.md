## 一、业务目标假设

| 假设项 | 说明 |
|--------|------|
| **MVP目标** | 快速上线验证市场，跑通"发布空岗 - 订阅匹配 - 沟通对接"核心闭环，同时以轻量AI能力降低用户使用门槛 |
| **核心关注** | 供需匹配效率（岗位与人才的连接速度和质量）、用户注册转化率、AI辅助带来的效率提升 |
| **目标用户** | 招聘者（B端，中小企业为主）+ 应聘者（C端，蓝领/灵活用工为主） |
| **MVP预期MAU** | 约1000人（招聘者~150人，应聘者~850人），基于种子用户冷启动估算 |
| **技术约束** | 依托微信生态（服务号 + 微信认证），降低获客门槛；AI能力优先采用成熟API服务，降低自研风险 |
| **运营约束** | 一期上线后由运营人员手动辅助完成企业认证审核、费用结算等管理工作 |
| **AI能力策略** | 一期AI聚焦"做减法"（OCR自动填充、内容审核等降低操作门槛），二期AI聚焦"做匹配"（语义搜索、画像匹配），三期AI聚焦"做生态"（行业洞察、面试教练） |

## 二、AI需求评估特殊说明

在对AI功能需求进行RICE评估时，需额外考虑以下维度，这些维度是传统功能评估中不涉及的：

### 2.1 Reach（触达）评估补充

| 考量维度 | 说明 |
|---------|------|
| **功能触发条件** | AI功能是否对所有用户生效，还是仅在特定操作时触发？例如OCR仅对上传营业执照的用户有效，而推送摘要对所有接收推送的应聘者有效 |
| **AI效果可见性** | 用户是否能直接感知AI的价值？隐性AI（如内容审核后台自动运行）vs 显性AI（如JD代写直接呈现结果） |
| **双端影响** | 部分AI功能虽部署在一端，但影响两端用户（如内容审核保护应聘者，岗位名称标准化帮助两端匹配） |

### 2.2 Effort（工作量）评估补充

AI功能的工作量包含全链路成本，远超同等复杂度的传统功能：

| 工作环节 | 说明 | 占比估算 |
|---------|------|:---:|
| **模型选型与接入** | 评估API服务商、接入SDK、协议对接 | 15% |
| **数据准备** | 训练数据收集/标注、知识库构建、同义词库/模板库整理 | 25% |
| **效果调优** | Prompt工程迭代、效果评估、准确率/召回率优化 | 30% |
| **降级方案** | AI不可用时的兜底策略（规则兜底、人工审核、默认模板等） | 15% |
| **集成测试** | 端到端测试、边界场景覆盖、性能压测 | 15% |

### 2.3 Confidence（信心）评估补充

| 信心等级 | 适用场景 | 说明 |
|:---:|------|------|
| **80%** | 成熟API能力 | OCR、内容审核等有成熟商业API的能力，效果可预期 |
| **70%** | 已验证LLM能力 | 文本摘要、智能回复等LLM基础能力，效果较好但需Prompt调优 |
| **60%** | 需领域适配 | JD代写、面试问题推荐等需要行业知识积累，效果取决于数据质量 |
| **50%** | 探索性能力 | 语义搜索、画像匹配、情感分析等深层AI能力，效果未经验证，MVP阶段数据不足 |

## 三、RICE评分明细

> **评分标准说明**
> - **R（Reach）**：每月影响用户数，基于MVP阶段预估MAU~1000人估算
> - **I（Impact）**：0.25（极低）/ 0.5（低）/ 1（中）/ 2（高）/ 3（极高）
> - **C（Confidence）**：百分比，传统功能通常为80%-100%，AI功能根据成熟度为50%-80%
> - **E（Effort）**：人月（1人月 = 1人工作20个工作日），AI功能含全链路工作量
> - **RICE Score** = (R x I x C) / E，数值越高优先级越高
> - **编号规则**：D=招聘者端、C=应聘者端、P=平台管理端、AI=AI功能需求

### 6.1 Must Have（不做则产品不可用）-- 12项（不变）

| 编号 | 需求 | 理由 |
|:---:|------|------|
| C01 | 微信认证注册（应聘者） | 用户入口，无此则无用户 |

| C06 | 与用人单位留言对话 | 供需对接闭环，匹配后必须有沟通通道 |

| D02 | 单位信息管理 | 招聘方身份基础数据，发布信息的前提 |
| D03 | 填写空岗信息 | 平台供给侧核心功能，无岗位则无匹配 |

## 八、决策记录

### 8.1 核心取舍决策

| 决策 | 取舍 | 理由 |
|------|------|------|
| **费用管理一期不做** | 舍弃在线支付，用线下/免费替代 | 资金合规复杂（支付牌照、对公账户），一期免费开放快速获客 |
| **会员管理一二三期不做** | 舍弃分级体系，运营手动标记 | 会员体系需要足够用户规模才有分级价值 |
| **企业认证非强制** | 允许未认证企业发布（标"待认证"标签） | 降低招聘者发布门槛，加速供给侧冷启动 |
| **数据统计简版** | 仅做基础计数，不做深度分析 | 一期数据量小，深度分析ROI低 |
| **基础管理最小化** | 仅做字段设置和职位库 | 一期岗位类型有限，人工辅助运营即可 |

### 8.2 AI功能 vs 传统功能 -- 资源分配核心决策

> 这是AI增强版本最关键的决策板块。AI功能与传统功能在资源争夺上有本质区别：AI开发的不确定性更高，但潜在回报也更大。

| 决策 | 资源分配取舍 | 理由 |
|------|------------|------|
| **增设AI团队（+2人），而非让传统团队兼顾AI** | 增加2人编制成本 vs 传统团队分心导致核心功能延迟 | AI开发需要专注的技术栈（LLM、CV、向量DB），让传统后端工程师兼任AI工作会导致两头不讨好。独立AI团队可并行工作，不阻塞核心功能开发 |
| **一期AI仅做API集成类功能，不做模型训练** | 放弃一期上线JD代写、语义搜索等高价值功能 | MVP阶段数据量不足以支撑模型训练，且模型调优周期不可控。一期AI聚焦调用成熟API（OCR、内容安全、LLM摘要），确保可控交付 |
| **AI-08推送摘要作为首批AI功能，优先于AI-09 JD代写** | 放弃JD代写在一期上线（尽管JD代写Impact更高=3） | AI-08的Confidence（80%）远高于AI-09（60%），且工作量仅0.5人月 vs 2.5人月。RICE Score 1920 vs 58，投入产出比差距33倍。先用低风险功能验证AI基础设施 |
| **AI-03内容审核优先于AI-06智能客服** | AI团队资源有限，内容审核排Sprint 2，智能客服排Sprint 3 | 内容审核影响所有发布内容（R=800）且有合规必要性；智能客服在一期咨询量小的情况下价值有限（I=0.5） |
| **二期AI核心投入语义搜索+画像匹配，而非JD代写+面试管理** | 语义搜索和画像匹配是平台核心差异化能力，JD代写和面试管理是效率工具 | 平台的核心价值是"匹配"，语义搜索+画像匹配直接提升匹配质量（I=2），且是竞品难以快速复制的技术壁垒。JD代写虽Impact高但属于通用能力，竞品可快速跟进 |
| **三期AI全部Won't，不投入任何预研资源** | 三期AI（面试教练、自适应测评等）技术门槛高，需大量数据积累 | 用户规模达到5000+之前，三期AI功能的数据基础不存在。过早投入预研是资源浪费。但建议在二期结束时开始收集相关数据（面试记录、测评结果等）为三期做数据储备 |
| **每个AI功能必须有降级方案** | 增加约15%的AI功能开发工作量 | AI服务存在不可控风险（API宕机、模型幻觉、网络延迟）。没有降级方案的AI功能等于引入单点故障。降级策略：OCR失败->手动填写，LLM失败->原始模板，审核失败->人工复核 |

### 8.3 AI功能优先级争议分析

| 争议需求 | 争议点 | 最终决策 | 决策依据 |
|---------|--------|---------|---------|
| **AI-08 推送摘要生成 vs AI-03 内容审核** | 两者都是一期Should AI，谁先做？ | **AI-03先（Sprint 2），AI-08同步** | AI-03是"防御型"AI（防止不良内容），AI-08是"进攻型"AI（提升体验）。平台安全优先于体验优化 |
| **AI-12 语义搜索 vs AI-13 画像匹配** | 二期两项核心AI能力，谁先做？ | **AI-12先（Sprint 5-6），AI-13后（Sprint 7-8）** | 语义搜索是画像匹配的数据基础（搜索行为数据可反哺画像模型），且语义搜索的用户感知更直接 |
| **AI-09 JD代写 vs AI-11 简历解析** | 两者Impact都是3，资源冲突时谁优先？ | **AI-11优先** | 简历解析是"数据基础"能力（解析后的结构化数据可支撑画像匹配、简历评分等多项下游AI），JD代写是"单点工具"。基础能力优先于应用功能 |
| **AI-01 OCR营业执照 vs AI-02 名片OCR** | 都是OCR，能否合并开发？ | **合并开发，AI-01优先** | 共享OCR基础能力（API接入、图片预处理），但AI-01绑定D04企业认证流程（Should），AI-02是纯便利功能（Could） |
| **AI-15 智能回复+情感分析 vs AI-05 基础智能回复** | 是否可以跳过AI-05直接做AI-15？ | **不可以，AI-05是一期基础** | AI-05建立对话上下文采集、LLM调用链路、降级框架等基础能力。AI-15在此基础上增加情感分析模块，渐进式开发风险更低 |
| **全部三期AI是否需要在二期预留接口？** | 预留接口增加二期工作量，不预留则三期重构成本高 | **仅预留数据埋点，不预留功能接口** | 数据埋点（面试记录、用户行为日志等）工作量小但对三期AI的数据积累至关重要。功能接口过度设计会拖慢二期进度 |

## 九、风险与依赖

### 9.1 传统功能风险

| 风险项 | 影响 | 缓解措施 |
|--------|------|---------|
| **微信服务号审核周期** | P01是核心基础设施，审核延迟将阻塞推送功能 | 尽早提交服务号申请（开发前2周），开发阶段使用测试号 |
| **微信认证接口变更** | C01/D01依赖微信OAuth接口稳定性 | 封装适配层，预留切换其他认证方式的接口 |
| **匹配算法冷启动** | 关键词匹配在初期岗位数量少时效果不佳 | 一期采用简单关键词匹配+人工推荐兜底 |
| **应聘者信息补充流失** | C04要求补充4类信息可能导致转化漏斗损耗 | 分步引导+进度条+跳过选项，监控每一步流失率 |
| **留言对话活跃度** | 双向沟通功能上线后可能使用率低 | 预设快捷回复模板+AI-05智能回复建议降低沟通门槛 |

### 9.2 AI特有风险

| 风险项 | 影响范围 | 严重程度 | 缓解措施 |
|--------|---------|:---:|---------|
| **AI服务质量不稳定** | 所有AI功能 | 高 | 每个AI功能必须有降级方案；AI服务网关统一封装超时/重试/降级逻辑；核心AI功能（审核、摘要）设人工兜底 |
| **LLM模型幻觉** | AI-08摘要、AI-05回复、AI-09 JD代写 | 高 | 输出内容增加事实性校验；用户可见的AI生成内容标注"AI生成"标识；建立用户反馈机制持续优化Prompt |
| **AI API成本超预期** | 所有调用外部API的AI功能 | 中 | 设定每日调用量上限和成本预警阈值；缓存高频请求结果；评估自建开源模型的成本对比点 |
| **数据隐私合规** | AI-11简历解析、AI-13画像匹配、AI-16简历评分 | 高 | 简历数据处理需用户明确授权；数据最小化原则（仅提取必要字段）；AI处理结果可被用户删除；遵守《个人信息保护法》 |
| **AI效果不及预期** | 二期AI（语义搜索、画像匹配） | 中 | 分阶段验证：先小范围灰度测试，效果达标再全量上线；保留传统关键词匹配作为回退方案 |
| **AI团队招聘困难** | 全部AI功能 | 高 | 如无法招到专职AI工程师，则：一期AI由后端工程师使用成熟API完成（工作量增加约30%）；二期AI延后到有AI人才时再启动 |
| **OCR识别准确率不足** | AI-01营业执照、AI-02名片 | 低 | 选用头部OCR服务商（准确率>95%）；识别失败自动降级为手动填写；人工复核机制 |
| **AI内容审核误判** | AI-03内容审核 | 中 | 设置误判反馈通道；初期保留人工复核（AI标记+人工确认）；随数据积累逐步提高自动化比例 |

### 12.2 AI vs 传统功能资源占比

> **报告结论**：v2.0 AI增强版在原有23项需求基础上新增30项AI功能需求，全量53项统一RICE排序。一期聚焦12个Must Have传统功能 + 8个一期AI功能（Should/Could级），用4个Sprint（8周）由7人团队（含2名AI工程师）并行交付。AI-08（推送摘要生成，RICE 1920）和AI-03（内容审核，RICE 800）是ROI最高的AI功能，应作为首批AI交付。二期（Sprint 5-8）重点投入语义搜索+画像匹配构建匹配壁垒。三期AI全部Won't，待用户规模和数据积累后再评估。核心风险在于AI团队招聘、AI服务稳定性和数据隐私合规，需提前应对。每个AI功能必须有降级方案，确保AI不可用时核心流程不受影响。
