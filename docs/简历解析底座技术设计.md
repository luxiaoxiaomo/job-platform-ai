# 简历解析底座技术设计

当前平台已经有求职者简历上传能力，但它只保存“当前简历”和一个临时快照。下一阶段需要把它升级成可追踪、可重跑、可接入 AI/RAG 的解析底座。这个底座不直接追求一次性做完整 AI 筛选系统，而是先把数据链路打稳：文件、原文、结构化字段、标签、关键词、chunk、解析任务、人工回写都要有明确边界。

本文参考两份资料：

- `STIC_AIGC_AI简历筛选功能说明书全新版本V1.3.docx`
- `技术文档/技术文档/技术设计/数据表设计/STIC_AIGC_表设计_0829.xlsx`

## 目标

第一阶段要做到：

1. 简历每次上传都有历史记录，不再只覆盖当前文件。
2. 上传后生成解析任务，任务有状态、错误原因和重跑入口。
3. 原始文件、抽取文本、结构化结果分层保存。
4. 支持最小结构化字段回写到求职者档案。
5. 预留标签、关键词、chunk 表，后续可接入 LLM、OCR、embedding、rerank。
6. 后台提示词管理能够覆盖简历解析、JD 解析、人岗匹配总结等场景。

非目标：

- 第一阶段不承诺高精度 AI 解析。
- 第一阶段不做完整 BERT/rerank 服务。
- 第一阶段不把所有 V1.3 页面字段一次性落库。
- 第一阶段不把画像和薪酬建议包装成真实 AI 结论。

## 当前现状

后端已有模块：

- `resume`: `seeker_resumes` 保存求职者当前最新简历。
- `seeker_profile`: 保存求职者基础档案。
- `ai_prompt`: 保存岗位预审提示词配置。
- `application`: 投递记录可使用当前简历快照。

当前 `seeker_resumes` 的职责过重：它同时承担当前文件、上传结果、解析快照。这个模型适合 MVP，但不适合后续追踪“哪一次上传、哪一次解析、哪一版提示词、哪一次回写”。

因此保留 `seeker_resumes` 作为“求职者当前生效简历指针”，新增解析底座表来承载过程数据。

## 核心流程

```text
求职者上传文件
  -> 创建 resume_uploads
  -> 更新 seeker_resumes 当前文件指针
  -> 创建 resume_parse_runs
  -> 抽取原文 resume_extracted_texts
  -> 切分 chunk resume_chunks
  -> 结构化解析 resume_structured_profiles
  -> 标签/关键词 resume_tags, resume_keywords
  -> 人工确认后回写 seeker_profiles
  -> 投递/匹配使用已确认快照
```

第一阶段可以同步执行简单解析，后续再切换为 Celery 异步任务。接口和表设计按异步状态设计，避免后续推翻。

## ER 关系

```text
users
  1 -> 1 seeker_profiles
  1 -> 1 seeker_resumes
  1 -> N resume_uploads

seeker_resumes
  1 -> N resume_uploads
  1 -> N job_applications

resume_uploads
  1 -> N resume_parse_runs
  1 -> N resume_extracted_texts
  1 -> N resume_chunks

resume_parse_runs
  1 -> 1 resume_extracted_texts
  1 -> N resume_chunks
  1 -> 1 resume_structured_profiles
  1 -> N resume_tags
  1 -> N resume_keywords
  1 -> N resume_profile_change_logs

ai_prompt_configs
  1 -> N resume_parse_runs
```

关系边界：

- `users` 是账号身份来源，`seeker_profiles` 是求职者确认后的资料。
- `seeker_resumes` 是当前生效简历指针，给个人中心、投递入口、简历状态快速读取。
- `resume_uploads` 是不可变上传历史，不因为重新上传而删除旧记录。
- `resume_parse_runs` 是可重跑解析任务，同一份上传文件可以有多次解析。
- `resume_structured_profiles` 是机器或规则解析结果，必须确认后才回写 `seeker_profiles`。
- `job_applications` 后续需要固化 `upload_id` 和 `parse_run_id`，避免求职者重新上传后污染历史投递。

## 状态机

上传状态：

```text
uploaded -> processing -> parsed
                    \-> failed
```

解析任务状态：

```text
pending -> running -> succeeded
                  \-> completed_with_errors
                  \-> failed
```

| 状态 | 所属对象 | 含义 | 用户可见文案 |
| --- | --- | --- | --- |
| `uploaded` | `resume_uploads` | 文件已保存，未开始解析 | 已上传 |
| `processing` | `resume_uploads` | 至少有一个解析任务正在执行 | 解析中 |
| `parsed` | `resume_uploads` | 最新解析任务成功 | 已解析 |
| `failed` | `resume_uploads` | 最新解析任务失败 | 解析失败 |
| `pending` | `resume_parse_runs` | 任务已创建，等待执行 | 等待解析 |
| `running` | `resume_parse_runs` | 正在抽取文本或解析 | 解析中 |
| `succeeded` | `resume_parse_runs` | 当前阶段要求的解析产物完成；P1 为原文和 chunk 入库成功 | 解析完成 |
| `completed_with_errors` | `resume_parse_runs` | 文件已保存，但部分解析产物失败；P1 常见于暂不支持的文件类型 | 部分完成 |
| `failed` | `resume_parse_runs` | 文件读取或解析完全失败 | 解析失败 |

重跑规则：

- 只有 `succeeded`、`completed_with_errors`、`failed` 的解析任务允许重跑。
- 重跑不覆盖旧 `resume_parse_runs`，而是创建新任务。
- 当前生效解析结果只通过 `seeker_resumes.current_parse_run_id` 或最新成功任务决定。
- 用户重新上传文件时，旧上传记录保留，当前简历指针切到新上传。

## 数据模型

### `seeker_resumes`

保留现有表，职责收窄为当前生效简历：

- `seeker_id`
- `file_url`
- `file_name`
- `content_type`
- `file_size`
- `parsed_snapshot`
- `updated_at`

后续可以新增：

- `current_upload_id`
- `current_parse_run_id`

这样投递时能固化使用的是哪一次上传和哪一次解析。

### `resume_uploads`

记录每一次上传。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 上传记录 ID |
| `seeker_id` | int | 求职者用户 ID |
| `resume_id` | int | 当前简历 ID，可为空，兼容创建顺序 |
| `file_url` | string | 文件访问路径 |
| `storage_path` | string | 服务端存储路径 |
| `original_file_name` | string | 原始文件名 |
| `content_type` | string | MIME |
| `file_ext` | string | 扩展名 |
| `file_size` | int | 文件大小 |
| `sha256` | string | 文件 hash，用于去重和追踪 |
| `upload_source` | string | `seeker_web/admin_import/api` |
| `status` | string | `uploaded/processing/parsed/failed` |
| `error_message` | text | 上传或解析失败原因 |
| `created_at` | datetime | 上传时间 |

索引：

- `(seeker_id, created_at desc)`
- `(sha256)`
- `(status, created_at)`

### `resume_parse_runs`

记录每一次解析执行。一次上传可以解析多次，因为提示词、模型、规则会变。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 解析任务 ID |
| `upload_id` | int | 上传记录 |
| `seeker_id` | int | 求职者 ID |
| `status` | string | `pending/running/succeeded/completed_with_errors/failed` |
| `parser_version` | string | 解析器版本 |
| `prompt_version` | int | 简历解析提示词版本 |
| `extractor` | string | `docx/pdf_text/ocr/mock/manual` |
| `started_at` | datetime | 开始时间 |
| `finished_at` | datetime | 结束时间 |
| `error_code` | string | 错误码 |
| `error_message` | text | 错误详情 |
| `metrics_json` | json/text | 页数、耗时、文本长度、chunk 数 |
| `created_at` | datetime | 创建时间 |

状态规则：

- `pending`: 已入队，未开始。
- `running`: 正在抽取或解析。
- `succeeded`: 当前阶段要求的解析产物都成功。P1 阶段只代表原文抽取和 chunk 入库成功，不代表 AI 结构化解析完成。
- `completed_with_errors`: 文件已保存，但部分解析产物失败；允许人工处理。
- `failed`: 文件无法读取或全部解析失败。

### `resume_extracted_texts`

保存原文抽取结果。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | ID |
| `parse_run_id` | int | 解析任务 |
| `upload_id` | int | 上传记录 |
| `text` | text | 抽取后的纯文本 |
| `text_hash` | string | 文本 hash |
| `language` | string | `zh/en/mixed/unknown` |
| `quality_score` | float | 简单质量分，0-1 |
| `page_count` | int | 页数 |
| `char_count` | int | 字符数 |
| `created_at` | datetime | 创建时间 |

质量分第一阶段可以按规则估算：

- 文本长度过短降分。
- 乱码比例高降分。
- 邮箱/手机号/年份/公司关键词存在加分。

### `resume_chunks`

RAG 的最小入库单元。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | chunk ID |
| `parse_run_id` | int | 解析任务 |
| `upload_id` | int | 上传记录 |
| `seeker_id` | int | 求职者 ID |
| `chunk_index` | int | 顺序 |
| `section` | string | `basic/education/work/project/skill/certificate/raw` |
| `content` | text | chunk 文本 |
| `content_hash` | string | 去重 |
| `token_count` | int | 估算 token 数 |
| `embedding_status` | string | `pending/embedded/failed/skipped` |
| `embedding_provider` | string | 后续填充 |
| `embedding_model` | string | 后续填充 |
| `vector_ref` | string | 外部向量库 ID，或后续 pgvector 字段 |
| `created_at` | datetime | 创建时间 |

第一阶段只存 chunk，不生成 embedding。后续可接 Qdrant、pgvector 或其他向量库。

### `resume_structured_profiles`

保存标准化简历结果。不要直接覆盖 `seeker_profiles`，先让用户确认。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | ID |
| `parse_run_id` | int | 解析任务 |
| `upload_id` | int | 上传记录 |
| `seeker_id` | int | 求职者 ID |
| `basic_json` | json/text | 姓名、性别、年龄、电话、邮箱、学历、工作年限 |
| `intention_json` | json/text | 目标岗位、城市、薪资、到岗时间 |
| `education_json` | json/text | 教育经历数组 |
| `work_json` | json/text | 工作经历数组 |
| `project_json` | json/text | 项目经历数组 |
| `skills_json` | json/text | 技能数组 |
| `certificates_json` | json/text | 证书和语言 |
| `self_review` | text | 自我评价 |
| `summary` | text | 简历摘要 |
| `confidence_json` | json/text | 字段置信度 |
| `source` | string | `rule/llm/manual/import` |
| `is_confirmed` | bool | 用户是否确认 |
| `confirmed_at` | datetime | 确认时间 |
| `created_at` | datetime | 创建时间 |

第一阶段字段可以只填：

- `basic_json.name`
- `basic_json.gender`
- `basic_json.education`
- `basic_json.work_years`
- `intention_json.target_position`
- `skills_json`
- `summary`

### 结构化 JSON 与明细表的关系

结构化 JSON 和明细表不是二选一，最终都需要。

`resume_structured_profiles` 的定位是解析结果载体，适合保存 LLM 或规则解析出来的完整结构、字段置信度、原始层级和未稳定字段。它允许我们在字段设计还没完全稳定时快速迭代，不会因为新增一个字段就频繁改表。

明细表的定位是业务查询和筛选载体。教育经历、工作经历、项目经历、技能、证书这些数据一旦字段稳定，就应该拆成规范化表，便于招聘者筛选、后台统计、人岗匹配、权限控制和数据质量治理。

建议演进顺序：

```text
P1: 原文 + chunk
P2: resume_structured_profiles 结构化 JSON + 核心规范化明细表
P3: 标签、关键词、筛选规则、匹配记录
```

P2 目标明细表：

| 表 | 说明 |
| --- | --- |
| `resume_basic_infos` | 简历解析出的基础信息快照，和 `seeker_profiles` 分离 |
| `resume_educations` | 教育经历 |
| `resume_work_experiences` | 工作经历和实习经历 |
| `resume_projects` | 项目经历 |
| `resume_skills` | 专业技能 |
| `resume_certificates` | 证书、奖项、语言能力 |

生成规则：

- JSON 是源解析结果，明细表是确认后或质量达标后的业务投影。
- 明细表必须记录 `parse_run_id`，保证能追溯到哪一次解析。
- 用户重新上传或重新解析时，不覆盖旧明细表；新建一组明细记录。
- 当前生效明细通过 `seeker_resumes.current_parse_run_id` 或确认状态判断。
- 如果字段置信度低，先留在 JSON，不进入明细表或标记为待确认。

提前建设明细表的原因：

- 简历筛选功能可以后做，但筛选依赖的数据底座不能后补。
- 学历、年限、学校、专业、公司、技能、证书这些字段是确定会被筛选和统计的稳定对象。
- 先建核心明细表，可以避免后续从历史 JSON 批量迁移时出现口径不一致。
- 当前阶段不要求每张表都填满，允许先写入高置信度字段，其余字段保留在 JSON。
- 明细表先服务数据治理和可追溯，筛选页面、筛选规则、复杂索引可以后续再做。

## 提示词场景

现有 `ai_prompt_configs.scenario_key` 只允许 `job_content_review`，需要扩展为以下场景：

| 场景 | 说明 |
| --- | --- |
| `job_content_review` | 岗位发布预审 |
| `resume_structured_parse` | 简历结构化解析 |
| `resume_tag_extract` | 简历标签提取 |
| `resume_keyword_extract` | 简历关键词提取 |
| `job_tag_extract` | JD 标签提取 |
| `job_keyword_extract` | JD 关键词提取 |
| `match_summary` | 人岗匹配总结、亮点、风险点 |
| `salary_estimation` | 薪酬规则或 AI 估算 |

每个提示词版本必须保存：

- `scenario_key`
- `version`
- `system_prompt`
- `user_prompt_template`
- `output_schema`
- `is_active`

解析结果需要记录使用了哪个 `scenario_key/version`，否则后续无法解释“为什么这次解析结果变了”。

查看解析任务队列。

```http
POST /api/v1/admin/resume-parse-runs/{id}/retry
```

管理员重跑解析。

```http
GET /api/v1/admin/resume-parse-runs/{id}/debug
```

查看抽取文本、提示词版本、错误信息、质量分。

## 解析策略

### 文件抽取

第一阶段按文件类型拆策略：

| 类型 | 策略 |
| --- | --- |
| `.docx` | 直接读取 Word XML 文本 |
| `.pdf` | 先尝试文本抽取，失败再标记需要 OCR |
| `.jpg/.png/.webp/.bmp` | 第一阶段标记 `ocr_pending`，后续接 OCR |
| `.doc/.xls/.xlsx` | 第一阶段允许上传，但可提示解析能力有限 |

上传成功不等于解析成功。前端要展示两个状态：

- 文件上传成功。
- 简历解析成功/失败/处理中。

### Chunk 策略

第一阶段规则：

- 原文小于 1500 字：一个 `raw` chunk。
- 原文较长：按段落合并，每个 chunk 约 600-1000 字。
- 如果能识别标题，则 section 标为 `education/work/project/skill`。
- chunk 必须保存 `parse_run_id`，避免后续简历更新后混用旧数据。

### 基础字段规则解析

在没有正式 LLM 前，先做低风险规则解析：

- 姓名：优先用户档案，简历文件名作为辅助，不强行覆盖。
- 手机：正则识别中国手机号。
- 邮箱：正则识别 email。
- 学历：按博士、硕士、本科、大专关键词取最高。
- 工作年限：从“X年经验”或工作经历日期估算，置信度低时不回写。
- 技能：从技能词典或关键词表匹配。

规则解析的结果要带置信度，前端展示为“待确认”，不能伪装成 AI 已准确解析。

## 人工确认与回写

解析结果不能直接覆盖求职者资料。正确流程：

```text
解析结果生成
  -> 前端展示差异
  -> 用户勾选要采用的字段
  -> 保存到 seeker_profiles
  -> 写 resume_profile_change_logs
```

这样可以避免当前出现的“页面显示还是旧名字”或“解析结果和个人资料不一致”的问题。

## 与投递和匹配的关系

投递时应该固化：

- `resume_id`
- `upload_id`
- `parse_run_id`
- `parsed_snapshot`

后续求职者重新上传简历，不应该影响历史投递。招聘者查看某次投递时，看到的是投递当时确认过的简历版本。

人岗匹配后续使用：

- `jobs` 的 JD 原文、标签、关键词、向量。
- `resume_chunks` 的原文 chunk。
- `resume_tags` 的结构化标签。
- `resume_keywords` 的关键词。
- `resume_structured_profiles` 的基础字段。

## 前端页面调整

求职者侧：

1. 上传页显示上传历史和最新解析状态。
2. 上传完成后进入“解析结果确认”页。
3. 原始简历和结构化结果分栏展示。
4. 支持重新上传、重新解析、手动修改字段。
5. 简历画像页面在正式 AI 解析前改成“基础信息画像”，避免误导。

管理端：

1. AI 监控里增加解析任务列表。
2. 提示词管理增加简历解析相关场景。
3. 增加解析失败列表，能看到失败原因和文件类型。

## 后端模块切分

建议在现有 `app/modules/resume` 内先扩展，不新建过多顶层模块：

```text
app/modules/resume/
  models.py
  schemas.py
  repository.py
  service.py
  extractors.py
  chunking.py
  parsing_rules.py
```

职责：

- `models.py`: 当前简历、上传、解析任务、原文、chunk、结构化结果。
- `schemas.py`: API 入参出参。
- `repository.py`: 简历相关持久化。
- `service.py`: 上传、状态、确认回写。
- `extractors.py`: docx/pdf/image 抽取策略。
- `chunking.py`: chunk 切分策略。
- `parsing_rules.py`: 第一阶段规则解析。

当解析能力变复杂后，再拆出：

- `resume_parse`: 解析任务和模型接入。
- `resume_rag`: chunk、embedding、检索。
- `resume_match`: 人岗匹配。

第一阶段保持在 `resume` 模块内，原因是当前代码规模还小，过早拆模块会增加跨模块调用和迁移成本。

## 迁移策略

数据库迁移分两步：

1. 兼容迁移：新增表和可空外键，不改变现有上传接口响应。
2. 接口升级：上传接口返回 `upload` 和 `parse_run`，前端开始消费解析状态。

现有数据处理：

- 为已有 `seeker_resumes` 补一条 `resume_uploads` 历史，状态设为 `parsed` 或 `uploaded`。
- 为已有 `parsed_snapshot` 补一条 `resume_parse_runs`，`extractor` 设为 `legacy_snapshot`。
- 如果没有原文文本，不强行生成 `resume_extracted_texts`，避免伪造数据。

回滚策略：

- 新表不影响旧 `seeker_resumes`，如果新上传流程出问题，可以让接口回退到旧保存逻辑。
- 前端如果读取不到 `upload/parse_run`，仍可展示当前 `resume`，但必须标记“解析状态未知”。

## 安全和权限

- 求职者只能读取、上传、确认自己的简历。
- 管理员可以查看解析任务和失败原因，但不默认下载原始简历文件。
- 原始简历包含电话、邮箱、身份证等敏感信息，管理端列表默认只展示摘要。
- 原文和 chunk 不应该进入普通日志。
- 后续接入 LLM 时，调用记录必须保存模型、提示词版本、输入摘要、输出摘要，不能把完整隐私文本写入业务日志。
- 文件访问路径要避免直接暴露服务端真实路径，API 只返回 `file_url`。

## 关键决策

### ADR-001：保留 `seeker_resumes`，新增上传和解析流水线表

状态：Accepted

背景：现有 `seeker_resumes` 已被投递和前端页面使用，直接替换风险大。但它无法表达上传历史和多次解析。

决策：保留 `seeker_resumes` 作为当前生效简历指针；新增 `resume_uploads` 和 `resume_parse_runs` 承载过程数据。

影响：

- 正向：兼容现有功能，降低改造风险。
- 负向：短期会有两层模型，需要明确同步规则。

### ADR-002：解析结果先确认，再回写个人资料

状态：Accepted

背景：简历解析存在误判，尤其是姓名、工作年限、学历、薪资意向等字段。

决策：`resume_structured_profiles` 作为解析结果，`seeker_profiles` 作为用户确认后的资料。

影响：

- 正向：避免 AI 或规则解析直接污染用户资料。
- 负向：前端需要增加确认交互。

### ADR-003：先存 chunk，后接 embedding

状态：Accepted

背景：RAG 是明确方向，但当前还没有确定向量库和 embedding 服务。

决策：第一阶段只把简历原文切成 `resume_chunks`，embedding 字段先留状态和引用。

影响：

- 正向：不会阻塞简历解析底座开发。
- 正向：未来可接 Qdrant、pgvector 或云向量库。
- 负向：第一阶段不能做真正语义检索。

### ADR-004：筛选功能后置，但核心明细表提前建设

状态：Accepted

背景：产品后续明确会扩展到简历筛选。筛选页面、筛选规则和匹配算法可以后做，但学历、工作年限、教育经历、工作经历、项目经历、技能、证书这些数据对象是确定的。如果前期只保存 JSON，后续需要批量迁移历史解析结果，容易产生字段口径不一致和数据追溯问题。

决策：P2 就建设核心规范化明细表，包括 `resume_basic_infos`、`resume_educations`、`resume_work_experiences`、`resume_projects`、`resume_skills`、`resume_certificates`。筛选功能本身不在 P2 交付范围内，P2 只要求明细表能承接确认后或高置信度的解析结果。

影响：

- 正向：后续做筛选、统计、人岗匹配时不需要推翻数据模型。
- 正向：历史解析结果从一开始就有结构化投影，减少迁移成本。
- 正向：JSON 仍保留完整解析结果，明细表只承接稳定和可查询字段。
- 负向：P2 表数量增加，需要控制字段范围，避免照搬完整企业 ATS 模型。

## 风险和处理

| 风险 | 处理 |
| --- | --- |
| 文档解析乱码 | 原文抽取后计算质量分，低质量进入人工处理 |
| PDF 或图片无法解析 | 上传成功但解析状态显示 `ocr_pending/failed` |
| AI 输出 JSON 不稳定 | 提示词配置必须带 output_schema，服务端做 schema 校验 |
| 重新上传影响历史投递 | 投递记录固化 `upload_id/parse_run_id/parsed_snapshot` |
| mock 数据误导测试 | 前端真实接口失败时明确显示错误，不静默回退 |
| 提示词变更导致结果不可解释 | 每次解析记录 prompt version |

## 最近可执行任务

建议下一步按这个顺序开发：

1. 修复当前简历快照乱码，并把画像页 mock AI 文案降级。
2. 建 `resume_uploads`、`resume_parse_runs`、`resume_extracted_texts`、`resume_chunks` 四张表。
3. 改上传接口：保存上传历史，创建解析任务，返回解析状态。
4. 做 `.docx` 原文抽取和 chunk 入库。
5. 前端上传页展示“上传历史 + 解析状态 + 原文预览”。
6. P2 立即补 `resume_structured_profiles` 和核心明细表，为简历筛选提前准备数据底座。

做到第 5 步，P1 的可追溯解析底座就能跑通。第 6 步开始进入 P2，把筛选未来一定会用到的结构化 JSON 和核心明细表补齐；筛选页面和复杂匹配规则仍然后置。

## 验收标准

P0 验收：

- 上传简历后，返回文案不是乱码。
- 个人中心、简历上传页不再把 mock AI 画像包装成真实解析结论。
- `python -m py_compile` 能通过相关后端模块。
- 前端构建通过。

P1 验收：

- Alembic 能创建 `resume_uploads`、`resume_parse_runs`、`resume_extracted_texts`、`resume_chunks`。
- 上传一份 `.docx` 简历后，数据库有一条上传记录、一条解析任务、一条原文记录和至少一个 chunk。
- `GET /api/v1/resumes/me` 能返回当前简历和最新解析状态。
- 重新上传不会删除旧上传记录。
- 解析失败时前端能看到明确失败状态，不静默显示 mock 成功。

P2 验收：

- `.docx` 能抽取基本原文。
- 至少能解析并展示姓名、学历、工作年限、目标岗位、技能摘要中的一部分。
- 结构化结果默认是待确认状态。
- `resume_structured_profiles` 能保存完整结构化 JSON 和字段置信度。
- Alembic 能创建 `resume_basic_infos`、`resume_educations`、`resume_work_experiences`、`resume_projects`、`resume_skills`、`resume_certificates`。
- 高置信度或用户确认后的解析结果能投影到核心明细表。
- 每条明细表记录都能追溯 `seeker_id`、`upload_id`、`parse_run_id`。
- 用户确认后才回写 `seeker_profiles`。
- 回写会生成 `resume_profile_change_logs`。

P3 验收：

- 提示词管理支持简历解析、简历标签、简历关键词、JD 标签、JD 关键词、人岗匹配总结场景。
- 每次解析能记录使用的提示词版本。
- 标签和关键词可以独立重跑，不需要重新上传文件。
- 简历筛选的候选条件和数据库索引设计完成，但筛选页面可以不在 P3 交付。

P4 验收：

- chunk 能进入 embedding 队列。
- 人岗匹配使用 `parse_run_id` 固定简历版本。
- 匹配结果包含分数、匹配理由、风险点和引用证据。
- 权重配置可追踪版本，历史匹配结果可解释。
