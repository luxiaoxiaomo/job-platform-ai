# R-P3-03 匹配规则配置化协作计划

## 背景

R-P3-01 已经完成规则版人岗匹配 API，R-P3-02 已经完成前端真实化联调。当前链路已经能基于求职者画像和真实岗位返回匹配分、维度分、亮点和差距。

现在的问题是，匹配规则还固化在后端代码里：

```text
技能 35%
经验 20%
学历 15%
城市 10%
薪资 10%
岗位意向 10%
```

这能支撑 V1 跑通，但不利于后续运营调参、不同岗位类型差异化匹配，也不利于解释“为什么是这个分”。R-P3-03 的目标是把规则版 V1 从“代码写死”推进到“后端可配置、前端可解释”。

## 目标

R-P3-03 不直接做向量匹配、LLM 自动评分或复杂推荐引擎。先把规则配置和解释能力打稳。

本阶段交付：

1. 后端提供默认匹配规则配置。
2. 匹配计算使用配置中的维度、权重、启停状态，并明确配置权重与实际生效权重的关系。
3. 匹配结果返回更完整的解释信息，前端能展示“分数怎么算出来的”。
4. 预留后续后台管理页可以调整权重，但本阶段可以先用种子数据或默认配置。
5. 保持现有 `GET /api/v1/matches/jobs/{job_id}/me` 兼容，不破坏 R-P3-02 页面。

## 不做范围

以下内容不放进 R-P3-03，避免范围失控：

- 不做向量库和语义相似度。
- 不做 LLM 实时生成匹配结论。
- 不做复杂多套规则模板，比如“销售岗模板”“技术岗模板”。
- 不做完整后台规则管理 UI，除非前端已有现成后台入口且改动很小。
- 不做岗位 JD 结构化解析表。当前仍基于现有岗位字段、标签和描述。
- 不做历史匹配记录沉淀表。可以在 P3-04/P4 单独做。

## 推荐拆分

- `GET /api/v1/matches/jobs/{job_id}/me` 兼容原前端字段。
- 返回 `rule_config` 或等价配置来源信息。
- 每个维度都有 `weight`、`score`、`explanation`，推荐补 `configured_weight`、`effective_weight`、`weighted_score` 和 `scoring_method`。
- 配置权重和生效权重分开返回：`configured_weights` 表示后台配置值，`effective_weights` 表示启停维度后的实际计算权重。
- 权重计算采用动态归一化：启用维度的配置权重总和可以不是 100，后端按比例归一化到 100 后计算总分。
- 配置异常处理：启用维度权重总和必须大于 0，否则拒绝启用或返回配置错误。
- 后端测试覆盖默认配置、正常匹配、无画像、下架岗位、权重参与总分计算。

### R-P3-03B 前端解释展示，Claude Code 负责

前端不需要等后台配置管理页完成。先在现有匹配分析页把后端返回的解释信息展示清楚。

页面调整建议：

1. 在总分区域下方展示规则名称，例如“默认人岗匹配规则 V1”。
2. 在分项得分区域展示权重和加权贡献，例如“技能匹配 80 分，权重 35%，贡献 28 分”。
3. 增加“分数怎么算”区域，展示每个维度的 `scoring_method`。
4. 保留当前亮点和待补充项。
5. 如果后端没有返回新字段，前端要 fallback 到旧字段，避免白屏。
6. 前端必须按后端返回的 `dimensions` 动态渲染，不写死 6 个维度，也不按 key 写展示分支。
7. 雷达图优先支持动态维度；如果维度数超过 8 个，前端可以降级成纵向分数条列表。

前端建议展示结构：

```text
AI 人岗匹配分析

总分 82
默认人岗匹配规则 V1

分项得分
- 技能匹配：80 分，权重 35%，贡献 28 分
- 经验年限：100 分，权重 20%，贡献 20 分

分数怎么算
- 技能匹配：岗位标签、岗位描述中的技能要求与简历技能做规则匹配
- 经验年限：简历工作年限与岗位经验要求做比较
```

前端验收：

- 旧接口字段仍可渲染。
- 新接口字段可展示规则名称、维度权重、加权贡献、解释方法。
- 维度数量变化时仍可渲染；后端新增“证书匹配”“项目经验匹配”等维度时，前端不需要改代码即可展示基础信息。
- 移动端文字不溢出，不遮挡雷达图和按钮。
- `profile_required`、`job_not_found`、普通失败状态仍正常。
- `npm.cmd run build` 通过。

### R-P3-03C 可选后台管理入口，暂缓或轻量实现

如果当前招聘端/管理端已有配置页框架，可以加一个只读页或轻量编辑页。

轻量版只做：

- 查看当前规则。
- 查看每个维度权重。
- 提示“配置编辑后续开放”。

编辑版暂不建议马上做，因为会引入权限、保存、启用、版本回滚、审计日志等问题。

## 后端数据设计建议

R-P3-03 可以先不落库，用代码默认配置对象完成。但如果要为后续后台配置铺路，建议新增两张表。

### `match_rule_configs`

```text
id
name
strategy
version
scope
status
description
parent_version_id
effective_from
effective_to
created_at
updated_at
```

字段说明：

- `scope`：配置适用范围。默认 `global`，后续可扩展为 `job_category:tech`、`job_category:sales`、`job_id:123`。
- `status`：规则状态。使用 `draft`、`active`、`testing`、`archived`，不要只用布尔值 `is_active`。
- `parent_version_id`：上一版本，用于后续回滚和版本链路。
- `effective_from` / `effective_to`：规则生效时间窗口，先预留字段，R-P3-03 可以不做复杂调度。

### `match_rule_dimensions`

```text
id
config_id
dimension_key
label
weight
effective_weight
enabled
description
scoring_method
logic_json
sort_order
created_at
updated_at
```

字段说明：

- `weight`：配置权重。
- `effective_weight`：一般不需要落库，可由后端运行时计算；如果落库，只作为快照字段。
- `scoring_method`：当前给前端展示的人类可读说明。
- `logic_json`：预留结构化规则描述，例如 `{"type": "keyword_match", "source": "tags"}`。R-P3-03 可以只返回空对象或不启用编辑。

当前建议：R-P3-03 可以先做服务层默认配置，schema 按可落库结构设计。若本轮要加 migration，必须包含 `scope`、`status`、`parent_version_id`、`effective_from`、`effective_to` 和 `logic_json`，避免后续配置后台重构。

## 权重归一化规则

后端必须明确区分两类权重：

```text
configured_weight：配置权重，来自默认配置或数据库。
effective_weight：实际参与总分计算的权重，按启用维度动态归一化。
```

计算规则：

```text
enabled_dimensions = dimensions where enabled = true
configured_total = sum(enabled_dimensions.configured_weight)
effective_weight = configured_weight / configured_total * 100
weighted_score = dimension_score * effective_weight / 100
overall_score = round(sum(weighted_score))
```

示例：如果禁用城市匹配，剩余配置权重总和为 90：

```text
技能 configured_weight=35，effective_weight=38.89
经验 configured_weight=20，effective_weight=22.22
学历 configured_weight=15，effective_weight=16.67
薪资 configured_weight=10，effective_weight=11.11
岗位意向 configured_weight=10，effective_weight=11.11
```

现有 `weights` 字段为了兼容前端继续保留，建议等同于 `effective_weights`。新增 `configured_weights` 和 `effective_weights`，让后续页面可以同时展示“后台配置”和“实际计算”。

1. Codex 先补后端配置 schema 和默认配置服务。
2. Codex 调整匹配服务使用配置计算总分，保持接口兼容。
3. Codex 补后端测试并更新看板。
4. Claude Code 接入新增字段，优化匹配分析页解释展示。
5. Claude Code 跑前端 build。
6. 双方用 `13800138000` 求职者账号做浏览器联调。
7. 联调通过后看板标记 R-P3-03 Done。

## 接口兼容原则

前端已经接入的字段不能删除或改名：

```text
job
overall_score
level
recommendation
summary
weights
dimensions
highlights
gaps
source
```

R-P3-03 只能新增字段：

```text
rule_config
configured_weights
effective_weights
dimensions[].weighted_score
dimensions[].configured_weight
dimensions[].effective_weight
dimensions[].scoring_method
dimensions[].description
dimensions[].logic
```

如果后续要改字段名，必须先做一版兼容期。

## 验收用例

后端用例：

1. 有画像、有 active 岗位：返回匹配结果，权重来自默认配置。
2. 无画像：返回 `422 profile_required`。
3. 岗位不存在或非 active：返回 `404 job_not_found`。
4. 默认配置下：配置权重总和为 100，总分等于各维度加权结果。
5. 禁用某个维度时：后端返回 `configured_weights` 和归一化后的 `effective_weights`，总分按 `effective_weights` 计算。
6. 启用维度权重总和为 0：拒绝配置或返回明确配置错误。

前端用例：

1. 匹配页能展示总分、等级、建议、雷达图。
2. 分项得分能展示权重和贡献分。
3. “分数怎么算”能展示每个维度解释。
4. 新老接口字段都能正常渲染。
5. 后端新增维度时，前端按 `dimensions` 动态渲染。
6. 移动端不出现文字重叠。

## 给 Claude Code 的确认点

Claude Code 可以重点确认这几个问题：

1. 匹配页是否需要单独做“分数怎么算”折叠区，还是直接放在分项得分下面？
2. `weighted_score` 前端是否要展示为整数，还是保留一位小数？
3. 规则名称展示在总分区是否合适？
4. 是否需要在岗位详情页的匹配入口展示“规则版 V1”标识？
5. 如果后端暂时只新增字段、不做后台配置页，前端是否足够推进 R-P3-03？
6. 维度超过 8 个时，Claude Code 是否同意从雷达图降级为分数条列表？

## 建议结论

R-P3-03 先做“后端配置结构 + 前端解释展示”，不急着做编辑后台。设计上接受 Claude Code 的扩展性建议：权重采用动态归一化，配置模型预留 `scope` 和 `status`，前端按后端返回的维度动态渲染。这样既能解决当前权重写死的问题，也能让用户看懂匹配分的来源，同时为后续规则后台、岗位类型模板、AB 测试和 LLM 解释留出空间。
