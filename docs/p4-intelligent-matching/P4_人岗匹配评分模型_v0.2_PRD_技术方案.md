# P4 人岗匹配评分模型 v0.2 PRD / 技术方案

## AI 速读卡

- 产品目标：把“岗位向量 + 人才向量 + 三维评分 + 画像完整度 + 真实行为质量”固化成可开发、可审计、可降级的人岗匹配 v0.2。
- 目标用户：平台管理员、规则运营、算法/产品评估人员；求职者和招聘者只消费匹配结果，不管理模型。
- P0 范围：向量文档设计、候选召回流程、五类分数组件、审计字段、离线评估、灰度接入边界。
- 当前事实：P4 已有智能策略与离线评估后端底座；真实向量召回、混合评分 adapter、运行时灰度分支还未完成。
- 核心公式：先硬条件过滤，再召回候选，再计算 `semantic_score/tag_score/keyword_score/profile_coverage_score/behavior_quality_score`，最后加权融合。
- 风控原则：城市、薪资、学历、经验、必需技能等硬约束优先于总分；高语义分不得覆盖硬缺口。
- 向量库原则：P0 先定义 adapter 和索引元数据，默认兼容 pgvector；后续可替换 Qdrant/Milvus，不把实现绑死。
- 验收重点：每个分数组件可解释、可回放、可写入 match audit；向量不可用时回退 P3 规则 baseline。

## 第一章：背景与目标

### 1.1 当前背景

`硬约束`：本方案承接现有 P3/P4 基线，不重做已有能力。

当前仓库事实如下：

- P3 已完成规则匹配、规则版本、AB 实验、匹配审计、发布治理和 Match Quality 看板。
- P4 已完成智能匹配策略与离线评估的后端最小闭环，包括 `intelligent_matching_strategies`、`intelligent_matching_evaluations` 以及策略 API。
- 运行时求职者/招聘者匹配仍使用规则 baseline。
- 向量召回、混合评分、智能策略 treatment 灰度、智能审计扩展和生产证据仍未完成。

所以 v0.2 的重点不是“部署一个向量库”，而是先把向量库要承载的数据、召回边界、评分公式、审计字段和开发切片定清楚。

### 1.2 产品目标

`硬约束`：v0.2 要回答四个问题。

1. 岗位向量和人才向量分别存什么。
2. 召回出来的人/岗候选如何进入人岗匹配。
3. 三维评分、画像分、行为分如何组合，如何防止误伤。
4. 后端、前端、数据和验收分别怎么落地。

### 1.3 不做事项

`硬约束`：v0.2 不做以下事项。

- 不让 LLM 实时打分替代规则或向量评分。
- 不自动改规则权重、不自动发布、不自动扩量。
- 不把 demo/mock 数据当作上线依据。
- 不直接改变招聘者候选人排序的正式线上逻辑。
- 不在向量服务不可用时影响现有 `GET /api/v1/matches/jobs/{job_id}/me` 可用性。

## 第二章：用户角色与使用场景

### 2.1 用户角色

| 角色 | P0 权限 | 说明 |
| --- | --- | --- |
| 平台管理员 | 管理策略、运行评估、查看审计 | 沿用现有 `admin` |
| 规则运营 | P0 不单独建角色 | 后续可拆成 `rule_operator` |
| 算法/产品评估人员 | P0 由 `admin` 代替 | 关注离线评估和灰度结果 |
| 求职者 | 查看本人岗位匹配结果 | 不看到策略配置 |
| 招聘者 | 查看投递/候选相关匹配解释 | P0 不启用智能排序 |

### 2.2 核心场景

场景 A：求职者看某岗位匹配度。

- 系统先使用岗位硬约束和求职者画像做基本可行性判断。
- 若命中智能策略 treatment 且向量可用，计算混合分。
- 若未命中或智能能力异常，返回 P3 规则 baseline。

场景 B：招聘者查看一个投递人的匹配解释。

- 系统沿用现有投递匹配入口。
- 智能分只作为解释增强，不改变 P0 排序。
- 审计记录必须能解释每个分数组件。

场景 C：管理员评估新策略能否灰度。

- 管理员创建或选择智能策略。
- 离线评估对比 baseline 与 hybrid。
- 样本不足或 demo/mock 占比不合规时，不允许输出上线结论。

场景 D：向量库或画像数据不可用。

- 系统回退规则 baseline。
- 审计记录 `degrade_reason`，用于 Match Quality 后续观察。

## 第四章：核心流程与状态机

### 4.1 人岗匹配总流程

```text
输入岗位/人才
  -> 标准化文本与结构化字段
  -> 硬约束过滤
  -> 规则 baseline 候选
  -> 向量召回候选
  -> 候选合并去重
  -> 五类分数组件计算
  -> 硬约束 cap / 降级处理
  -> final_match_score
  -> 写入 match audit
  -> 返回结果或离线评估报告
```

### 4.2 双向召回流程

求职者找岗位：

```text
talent_profile_vector -> search job_vector_index -> candidate jobs
```

招聘者找人才：

```text
job_vector -> search talent_vector_index -> candidate talents
```

`硬约束`：两个方向可以共用评分服务，但不能共用权限边界。人才侧召回不得返回手机号、邮箱、原始简历全文等敏感信息。

### 4.3 策略状态

沿用现有智能策略状态：

| 状态 | 含义 | 允许动作 |
| --- | --- | --- |
| `draft` | 策略草稿 | 编辑、评估、克隆 |
| `evaluating` | 正在或刚完成离线评估 | 查看报告、调整参数 |
| `testing` | 可被灰度 treatment 引用 | 创建实验、观察、暂停 |
| `active` | 通过治理后成为默认智能策略 | P0 不要求实现 |
| `archived` | 历史只读 | 查看、克隆 |

### 4.4 降级状态

| `degrade_reason` | 触发条件 | 行为 |
| --- | --- | --- |
| `vector_unavailable` | 向量服务超时、连接失败、索引不存在 | 回退规则 baseline |
| `vector_stale` | 索引版本落后于数据版本 | 回退或标记低置信 |
| `missing_job_vector` | 岗位未完成 embedding | 仅使用规则/标签/关键词 |
| `missing_talent_vector` | 人才画像未完成 embedding | 仅使用规则/标签/关键词 |
| `profile_incomplete` | 画像覆盖分低于阈值 | 降低语义分权重，必要时回退 |
| `hard_constraint_failed` | 城市/薪资/学历/经验/必需技能硬约束不满足 | 不推荐或总分 cap |
| `audit_write_failed` | 智能审计无法写入 | 不返回不可追溯智能结果 |

### 6.2 向量库选择

`推荐默认`：P0 使用 adapter-first 设计，默认兼容 PostgreSQL + pgvector；如果后续数据量、延迟或运维要求变化，再替换为 Qdrant/Milvus。

理由：

- 现有架构文档已偏向 PostgreSQL + pgvector。
- 当前还未部署向量库，先绑定重型组件会增加实现风险。
- adapter 能让 BE-P4-04/05 先完成接口、降级和测试。

最低接口：

```python
class VectorRecallAdapter:
    async def upsert(document: VectorDocument) -> VectorUpsertResult: ...
    async def search(query: VectorQuery) -> VectorRecallResult: ...
    async def delete(entity_type: str, entity_id: int) -> None: ...
    async def health() -> VectorIndexHealth: ...
```

### 6.4 五类评分组件

#### 6.4.1 `semantic_score`

含义：岗位文本与人才画像文本的语义相似度。

来源：

- 向量召回相似度。
- 或离线评估中 adapter 返回的 deterministic similarity。

归一化：

```text
if similarity < min_similarity:
  semantic_score = 0
else:
  semantic_score = round((similarity - min_similarity) / (1 - min_similarity) * 100)
```

`硬约束`：

- 必须记录原始 `similarity` 和归一化 `semantic_score`。
- `semantic_score` 不得覆盖硬约束失败。
- 向量缺失时该分数为 `null`，不是 `0`；是否降级由策略决定。

#### 6.4.2 `tag_score`

含义：岗位标签、标准职位、技能标签与人才标签的结构化匹配度。

推荐公式：

```text
tag_score =
  skill_tag_score * 0.50 +
  standard_position_score * 0.25 +
  industry_or_function_score * 0.15 +
  preference_tag_score * 0.10
```

计算规则：

- 技能标签使用加权 Jaccard。
- 标准职位完全命中为 100，同类目命中为 70，不相关为 30。
- 停用标签不参与新计算，但历史审计保留名称快照。

#### 6.4.3 `keyword_score`

含义：岗位要求关键词与简历/人才画像关键词的直接命中程度。

推荐公式：

```text
keyword_score =
  required_keyword_hit_rate * 0.70 +
  preferred_keyword_hit_rate * 0.20 +
  negative_keyword_penalty_adjustment * 0.10
```

`硬约束`：

- 必需关键词未命中时，不能只靠语义分抬高到强推荐。
- 关键词来源必须可回溯到岗位要求、岗位标签、简历技能或结构化经历。

#### 6.4.4 `profile_coverage_score`

含义：人才画像完整度和可评分可信度，不代表匹配好坏。

推荐打分：

| 画像项 | 权重 | 有效条件 |
| --- | --- | --- |
| 简历解析确认 | 10 | 有最新确认过的结构化解析 |
| 求职意向 | 15 | 目标岗位、求职城市、求职状态至少两项有效 |
| 薪资与到岗信息 | 10 | 期望薪资、到岗时间或工作状态有效 |
| 技能标签 | 20 | 至少 3 个标准化技能/标签 |
| 工作经历 | 20 | 年限、公司/项目、职责或成果结构化 |
| 教育/证书 | 10 | 学历或证书字段有效 |
| 更新时间与一致性 | 15 | 90 天内更新，且关键字段无明显冲突 |

字段状态：

```text
valid = 1.0
weak = 0.5
missing = 0
```

公式：

```text
profile_coverage_score = round(sum(item_weight * item_state))
```

`硬约束`：

- `profile_coverage_score` 最高只作为 5%-10% 的可信度修正项。
- 分数低于 60 时，语义分权重不得高于 20%，并记录 `profile_incomplete`。
- 分数不能让本来不匹配的人才变成强推荐。

#### 6.4.5 `behavior_quality_score`

含义：真实业务行为对“这个匹配是否靠谱”的反馈质量。

P0 决策：

- 字段、权重、审计先保留。
- 默认不参与生产实时总分。
- 只有真实样本达到阈值后，才能进入灰度。

推荐信号：

| 信号 | 分值影响 | 说明 |
| --- | --- | --- |
| 求职者有效浏览岗位 | +3 | 排除极短停留 |
| 求职者收藏岗位 | +8 | 对岗位感兴趣 |
| 求职者投递岗位 | +15 | 强正向 |
| 招聘者查看候选详情 | +5 | 轻正向 |
| 招聘者收藏/标记候选 | +10 | 中正向 |
| 双方发生有效沟通 | +15 | 强正向 |
| 面试邀请/接受 | +20 | 强正向 |
| 人工标记合适 | +25 | 强正向 |
| 录用/入职反馈 | +35 | 最强正向，P1 后使用 |
| 快速跳出/误点 | -5 | 轻负向 |
| 沟通无响应 | -8 | 需按角色区分 |
| 因硬条件拒绝 | -20 | 例如城市、薪资、经验明显不符 |
| 爽约/投诉/违规 | -30 到 -50 | 强负向，需审计 |

推荐公式：

```text
behavior_quality_score = clamp(50 + positive_signal_score - negative_signal_score, 0, 100)
```

样本阈值：

| 条件 | 行为分状态 |
| --- | --- |
| pair 级真实行为少于 3 条 | `null`，不参与实时总分 |
| cohort 级真实样本少于 30 | 只用于离线观察 |
| cohort 级真实样本 30-99 | 可进入灰度，但显示低置信 |
| cohort 级真实样本 >= 100 | 可作为 P1 权重候选 |

`硬约束`：

- 无行为样本时，`behavior_quality_score` 是 `null`，不是 `0`。
- 默认 `behavior_quality_weight = 0`，不得因为缺少行为样本惩罚所有候选。
- 行为分进入生产前必须经过偏差审查，避免只强化已有曝光带来的马太效应。

### 6.5.0 分数语义与字段兼容

`硬约束`：实现时必须区分“评分组件”和“策略配置字段”，不能因为字段名相近而混用。

当前后端策略配置已经存在 `hybrid_weights`，字段为：

```json
{
  "rule_score": 0.7,
  "vector_score": 0.2,
  "profile_coverage_score": 0.1,
  "behavior_quality_score": 0
}
```

v0.2 的开发约定如下：

| 层级 | 字段 | 含义 | P0 处理方式 |
| --- | --- | --- | --- |
| 策略配置 | `rule_score` | 现有 P3 规则 baseline 或结构化规则分的权重 | 保持 API 兼容，不在 P0 改名 |
| 策略配置 | `vector_score` | 语义向量贡献权重 | 对应 `semantic_score` 的策略层权重 |
| 策略配置 | `profile_coverage_score` | 画像可信度权重 | 默认 5%-10%，不得扩大为主分 |
| 策略配置 | `behavior_quality_score` | 行为质量权重 | 默认 0，样本达标后才可灰度 |
| 评分明细 | `semantic_score` | 向量语义相似度归一化得分 | 写入 `score_components` |
| 评分明细 | `tag_score` | 标签、标准职位、技能结构化匹配得分 | 写入 `score_components` |
| 评分明细 | `keyword_score` | 必需/加分关键词命中得分 | 写入 `score_components` |
| 评分明细 | `base_match_score` | 三维主分融合结果 | 写入 `score_components` |
| 评分明细 | `final_match_score` | cap 和降级后的最终展示/排序参考分 | 写入 `score_components` |

`推荐默认`：BE-P4-05 不强制迁移已落库策略字段。评分服务内部输出五类明细分，并在审计里同时记录：

- `configured_weights`：策略配置原值。
- `actual_component_weights`：本次计算实际使用的组件权重。
- `weight_redistribution_reason`：发生权重重分配时的原因。

这样既兼容已完成的 P4 策略 API，又能让新评分模型可解释、可回放。

### 6.5 总分公式

#### 6.5.1 三维主分

保留用户此前的三维评分模型：

```text
base_match_score =
  semantic_score * 0.50 +
  tag_score * 0.30 +
  keyword_score * 0.20
```

若 `semantic_score = null`：

```text
base_match_score =
  tag_score * 0.60 +
  keyword_score * 0.40
```

#### 6.5.2 v0.2 推荐融合公式

生产默认：

```text
final_match_score =
  base_match_score * 0.95 +
  profile_coverage_score * 0.05
```

行为分达到灰度阈值后：

```text
final_match_score =
  base_match_score * 0.90 +
  profile_coverage_score * 0.05 +
  behavior_quality_score * 0.05
```

行为分达到 P1 稳定阈值后，可评估：

```text
final_match_score =
  base_match_score * 0.85 +
  profile_coverage_score * 0.05 +
  behavior_quality_score * 0.10
```

`硬约束`：

- 每次计算必须记录实际使用的权重，不只记录默认权重。
- 缺失分数组件不得默认为 0 参与惩罚，必须显式降级或权重重分配。
- `final_match_score` 是排序/推荐参考，不替代硬约束判断。

#### 6.5.3 `null`、`0` 与权重重分配

`硬约束`：`null` 表示能力不可用或样本不足，`0` 表示已经完成计算且结果为 0。两者不能混用。

| 组件 | 允许为 `null` | `0` 的含义 | 权重处理 |
| --- | --- | --- | --- |
| `semantic_score` | 允许，表示向量不可用、缺失或超时 | 相似度低于阈值且已完成计算 | `null` 时移除语义权重，回退标签/关键词或 baseline |
| `tag_score` | 仅在标签体系不可用时允许 | 标签已计算但无有效命中 | `null` 时记录 `tag_unavailable`，不能伪造为 0 |
| `keyword_score` | 仅在关键词抽取不可用时允许 | 关键词已计算但无命中 | `null` 时记录 `keyword_unavailable`，必要时回退 baseline |
| `profile_coverage_score` | 原则上不为 `null` | 画像完全缺失或不可评分 | 只作为可信度修正；低分触发 cap 或提示补全 |
| `behavior_quality_score` | 允许，表示真实样本不足 | 行为样本足够且净反馈极差 | `null` 时权重强制为 0，不惩罚候选 |

权重重分配规则：

```text
available_weight = sum(weights of non-null components)
if available_weight == 0:
  degrade to rule_baseline
else:
  actual_weight(component) = configured_weight(component) / available_weight
```

例外：

- `profile_coverage_score` 的实际权重不得因为其他组件缺失而超过 10%。
- `behavior_quality_score` 未达样本阈值时，实际权重必须为 0。
- 硬约束失败时，不通过权重重分配绕过 cap。
- 审计写入失败时，不返回 hybrid 智能分。

### 6.6 硬约束与 cap 规则

| 条件 | 行为 |
| --- | --- |
| 岗位非 active | 不参与召回 |
| 城市完全不匹配且岗位不支持异地 | final cap 59 |
| 薪资无交集且双方都填了薪资 | final cap 69 |
| 学历低于硬要求两档以上 | final cap 59 |
| 经验低于硬要求超过 3 年 | final cap 69 |
| 必需技能命中率低于 50% | final cap 69 |
| 画像覆盖分低于 40 | final cap 69，并提示补全画像 |
| 投诉/违规强负向 | 不推荐，进入风控审查 |

`推荐默认`：cap 后仍保留原始分数组件，便于运营知道“为什么语义高但最终不推荐”。

### 6.7 指标定义

`vector_recall_coverage`：

- business meaning：样本中可被向量召回覆盖的比例。
- numerator：有有效向量召回结果的样本数。
- denominator：评估或灰度样本总数。
- data source：vector recall result + match audit。
- refresh cadence：离线评估时计算；线上按审计聚合。
- caveats：覆盖率高不代表质量高。

`profile_coverage_avg`：

- business meaning：参与匹配的人才画像平均完整度。
- numerator：样本 `profile_coverage_score` 之和。
- denominator：样本数。
- data source：seeker profile、resume structured profile、match audit snapshot。
- refresh cadence：评估/审计聚合。
- caveats：只表示可评分可信度。

`behavior_quality_available_rate`：

- business meaning：有足够行为样本可计算行为分的比例。
- numerator：`behavior_quality_score != null` 的样本数。
- denominator：样本数。
- data source：job visits、favorites、applications、messages、contact exchange、manual review。
- refresh cadence：每日或评估时。
- caveats：行为有延迟和曝光偏差。

`degrade_rate`：

- business meaning：智能分支回退或部分降级比例。
- numerator：`degrade_reason != null` 的智能策略匹配次数。
- denominator：智能策略 treatment 匹配次数。
- data source：match audit。
- refresh cadence：Match Quality 聚合。
- caveats：高降级率通常说明索引、画像或服务可用性不足。

`offline_win_rate`：

- business meaning：hybrid 在离线样本上优于 baseline 的比例。
- numerator：hybrid 排序/分层优于 baseline 的样本数。
- denominator：有可判断标签的样本数。
- data source：offline evaluation。
- refresh cadence：每次评估。
- caveats：demo/mock 不得支持上线结论。

## 第九章：异常、空状态与边界场景

### 9.1 空状态

- 无岗位向量：策略可以保存，但不能进入 runtime testing。
- 无人才向量：回退规则 baseline。
- 无画像：返回低可信匹配，提示补全画像。
- 无行为数据：行为分为 `null`，不参与总分。
- 无审计数据：Match Quality 不生成智能结论。

### 9.2 异常场景

- 向量服务超时：回退 baseline，`degrade_reason=vector_unavailable`。
- 索引版本过期：回退或低置信，`degrade_reason=vector_stale`。
- 策略权重非法：接口返回 400/422。
- 智能实验配置非法：不允许 running。
- 审计写入失败：不返回智能结果。

### 9.3 边界场景

- 同一候选同时来自规则和向量：合并候选，记录 `rule_and_vector`。
- 向量新增候选规则分很低：进入 cap，不得高排。
- 画像分很高但岗位不匹配：不能提升为强推荐。
- 行为分强但来自 demo/mock：只作演示，不作上线证据。
- 旧审计没有智能字段：显示 baseline，不回填伪数据。

## 第十一章：开发者交接说明

你接下来实现的不是一个黑盒推荐模型，而是一个可审计的五分数组件评分系统。

优先顺序：

1. 先做向量文档和 adapter，不急着绑定具体向量库。
2. 再做 scoring service，保证三维主分、画像分、行为分都可单测。
3. 再接 runtime treatment，默认仍保持规则 baseline。
4. 最后扩展审计和 Match Quality。

不要重新解释这些硬约束：

- P3 规则 baseline 是安全底座。
- 向量召回是候选补充，不是最终决策。
- 画像分是可信度，不是匹配度。
- 行为分样本不足时不参与生产实时总分。
- 硬条件优先于总分。
- demo/mock 不能作为上线证据。
- 智能结果必须能写审计，不能只返回一个分数。
