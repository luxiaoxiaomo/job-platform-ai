## 🎯 核心发现：3个关键遗漏

### 1. 简历明细表缺失（🔴 最关键）

**问题**：你的设计只有 `resume_structured_profiles` 存 JSON：

```json
{
  "education_json": [...],
  "work_json": [...],
  "skills_json": [...]
}
```

**但缺失了明细表**（STIC 原始设计有，用于业务查询）：
- `resume_educations` - 教育经历明细
- `resume_work_experiences` - 工作经历明细
- `resume_projects` - 项目经历明细
- `resume_skills` - 技能明细
- `resume_certificates` - 证书明细
- `resume_languages` - 语言能力明细

**为什么需要？**

| 场景 | JSON字段 | 明细表 |
|------|---------|--------|
| 筛选"有阿里工作经历" | ❌ `WHERE work_json::text LIKE '%阿里%'` 慢 | ✅ `JOIN work_experiences WHERE company='阿里'` |
| 统计学历分布 | ❌ 复杂、性能差 | ✅ `GROUP BY edu_degree` 快速 |
| 技能精确匹配 | ❌ JSON 数组难精确匹配 | ✅ `WHERE skill_name IN ('Java', 'Spring')` |

**你在第289行提到**：
> "结构化 JSON 和明细表不是二选一，最终都需要。"  
> "P2: resume_structured_profiles（JSON）+ 核心规范化明细表"

**但你没写具体明细表设计** ⚠️

**我的建议**：
- ✅ **P2 阶段必须补充这 6 张明细表**
- ✅ **双轨存储**：JSON 保留（灵活、迭代快），明细表用于业务查询（性能、筛选）
- 📝 **数据流**：解析结果 → `resume_structured_profiles` (JSON) → 用户确认 → 拆分存入明细表

**问题**：
- 你同意补充这 6 张表吗？
- 明细表什么时候生成？解析完立即生成，还是用户确认后？
- 明细表是否需要 `parse_run_id` 字段（追溯哪次解析生成的）？

### 2. 岗位JD解析表缺失（🔴 关键）

**问题**：你的设计只关注了**简历解析**，但 STIC 需求和原始表设计都有**岗位JD解析**。

**STIC 原始表**：`hhr_ta_position_recognition` - 岗位信息解析表

**V1.3 需求明确要求**：
- 岗位JD也需要：标签提取（8维度）、关键词提取（6维度）、向量化
- 人岗匹配时需要 `jd_vector` 和 `resume_vector` 做语义相似度

**当前空岗平台**：
- `jobs` 表只有原始 JD 字段（`requirements`, `responsibilities`）
- **没有岗位解析结果存储**

**我的建议**：
- 🎯 **新增 `job_parsed_profiles` 表**（对应简历的 `resume_structured_profiles`）

```sql
CREATE TABLE job_parsed_profiles (
  id BIGINT PRIMARY KEY,
  job_id BIGINT NOT NULL,  -- 关联 jobs.id
  parse_version VARCHAR(50),  -- 解析版本
  requirements_json JSON,  -- 结构化要求
  responsibilities_json JSON,  -- 结构化职责
  jd_vector BLOB,  -- JD向量（embedding）
  tags_json JSON,  -- 岗位标签（8维度）
  keywords_json JSON,  -- 岗位关键词（6维度）
  created_at DATETIME
);
```

**问题**：
- 岗位JD解析表你觉得需要吗？
- 是直接在 `jobs` 表加字段，还是独立表？
- 岗位也需要像简历一样的"解析任务状态机"吗？

### 3. 提示词场景扩展（🔴 关键）

**问题**：空岗平台当前 `ai_prompt_configs` 表只有 **1 个场景**：

```sql
scenario_key = 'job_content_review'  -- 岗位发布预审
```

**但 V1.3 需求需要至少 8 个场景**：
1. `resume_structured_parse` - 简历结构化解析
2. `resume_tag_extract` - 简历标签提取（16维度）
3. `resume_keyword_extract` - 简历关键词提取（校招8维/社招10维）
4. `job_tag_extract` - 岗位标签提取（8维度）
5. `job_keyword_extract` - 岗位关键词提取（6维度）
6. `match_summary` - 人岗匹配总结
7. `salary_estimation` - 薪酬规则估算
8. `resume_highlights_risks` - 简历亮点/风险分析

**你的设计**（第 681 行）：
> "扩展提示词场景：简历解析、标签提取、关键词提取、匹配总结"

**但你没写具体怎么扩展** ⚠️

**我的建议**：
- 📝 **P2 阶段**：扩展 `scenario_key` 枚举值
- 📝 **新增字段**：`output_schema` (JSON Schema，用于 LLM 结构化输出验证)
- 📝 **版本管理**：解析结果记录使用的提示词版本号

**问题**：
- `ai_prompt_configs` 表结构需要改吗？
- 提示词版本化怎么做？（同一场景可能有多个版本）
- LLM 输出验证用 JSON Schema 还是 Pydantic？

### 6. 软删除 vs 硬删除

**问题**：你的设计所有表都是物理删除（DELETE），但简历是核心资产，误删风险高。

**建议**：简历相关表加 `deleted_at` 字段（软删除）

你觉得呢？

- 下载简历

- 删除简历

需要 `audit_logs` 表吗？优先级？

### 8. 向量索引方案

**问题**：pgvector 有两种索引类型：

```sql
-- 选项A：IVFFlat（适合中等数据量，快速构建）
CREATE INDEX ON resume_chunks USING ivfflat (embedding vector_cosine_ops);

-- 选项B：HNSW（适合大数据量，查询更快，但构建慢）
CREATE INDEX ON resume_chunks USING hnsw (embedding vector_cosine_ops);
```

你倾向哪个？还是先不加索引？

---

### 9. 社会实践经历表

**STIC 原始表**：`hhr_ta_social_exp` - 社会经历表

**用途**：校招候选人的社会实践、志愿服务、学生干部

**问题**：我们做校招吗？需要这张表吗？
