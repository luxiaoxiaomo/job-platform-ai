# 基础数据与标签治理流程

Date: 2026-06-23
Scope: standard positions, tag library, public consumers, operation logs, impact checks
Owner role: `admin`

## 目标

标准职位库和标签库是岗位发布、求职意向、结构化简历、搜索、匹配质量分层和前台展示的共享基础数据。本流程定义新增、编辑、停用和验收规则，避免基础数据变更破坏业务闭环或让历史数据失去可解释性。

## 数据对象

### Standard Position

核心字段：

| Field | Governance Meaning |
| --- | --- |
| `name` | 标准职位名称，必须唯一 |
| `category` | 职位类目，用于搜索、匹配质量分层和运营统计 |
| `aliases` | 别名，用于岗位/简历标准化和搜索召回解释 |
| `description` | 管理说明，不作为用户侧强承诺 |
| `status` | `active` or `inactive`；public API 只返回 active |

### Tag Library Item

核心字段：

| Field | Governance Meaning |
| --- | --- |
| `name` | 标签名称，同 category 下必须唯一 |
| `category` | 标签类别，例如技能、行业、福利、岗位属性 |
| `parent_id` | 父级标签；不能指向自己 |
| `color` | UI 展示辅助，不应承载业务逻辑 |
| `sort_order` | 展示排序 |
| `status` | `active` or `inactive`；public API 只返回 active |

## 新增规则

### 新增标准职位

新增前检查：

[OK] `name` 不与现有标准职位重复。
[OK] `category` 已存在或有明确运营归类理由。
[OK] `aliases` 不包含明显冲突的其他岗位名称。
[OK] 已确认新增职位会被哪些业务页消费。

操作：

1. 管理员在 `/admin` 基础数据职位页新增。
2. 后端调用 `POST /api/v1/base-data/standard-positions`。
3. 系统写入 `base_data_operation_logs`，action = `create`。
4. 在 public API 中确认 active 职位可读。

验收：

[OK] Admin 列表可见。
[OK] Admin 详情页可打开。
[OK] Public API 可读取 active 记录。
[OK] 操作日志存在 before = null, after = 新记录快照。

### 新增标签

新增前检查：

[OK] 同 category 下 `name` 不重复。
[OK] `parent_id` 存在且不是自身。
[OK] `category` 与现有筛选/展示场景一致。
[OK] 标签不会替代已有标准职位或状态标签。

操作：

1. 管理员在 `/admin` 标签库页新增。
2. 后端调用 `POST /api/v1/base-data/tags`。
3. 系统写入 `base_data_operation_logs`，action = `create`。
4. 在 public tags API 中确认 active 标签可读。

验收：

[OK] Admin 标签列表可见。
[OK] Admin 标签详情页可打开并显示父级信息。
[OK] Public API 可读取 active 标签。
[OK] 操作日志存在 before = null, after = 新记录快照。

## 编辑规则

### 编辑标准职位

允许编辑：

[OK] 修正名称错别字或规范命名。
[OK] 补充 aliases。
[OK] 调整 category，但必须做影响检查。
[OK] 更新 description。

编辑前影响检查：

| Consumer | Check |
| --- | --- |
| Jobs | 检查是否有 `jobs.standard_position_id` 指向该职位；若改 category/name，确认岗位详情、搜索和匹配解释仍可读 |
| Seeker intent | 检查 `seeker_profiles.standard_position_id` 是否指向该职位；避免求职意向显示断裂 |
| Structured resume profiles | 检查结构化简历画像中的标准职位映射是否需要同步说明 |
| Search | 检查职位名、类目和 aliases 改动是否影响岗位搜索/候选人搜索召回 |
| Match Quality segments | 检查 `standard_position` 和 `position_category` 分层口径是否会发生前后不可比 |
| Public consumers | 检查前台岗位发布、求职意向选择器、候选人筛选是否继续读取 active 职位 |

操作：

1. 管理员编辑字段。
2. 后端调用 `PUT /api/v1/base-data/standard-positions/{position_id}`。
3. 系统写入 operation log，action = `update`。
4. 在详情页查看 before/after 操作日志。

### 编辑标签

允许编辑：

[OK] 修正标签名称。
[OK] 调整 category 或 parent_id。
[OK] 更新 color、sort_order、description。

编辑前影响检查：

| Consumer | Check |
| --- | --- |
| Jobs | 检查 `jobs.tag_refs` 和岗位详情标签展示 |
| Seeker intent | 检查求职者标签/意向选择是否仍能展示 |
| Structured resume profiles | 检查 `resume_structured_profiles.tag_refs` 的历史标签解释 |
| Search | 检查岗位搜索、候选人搜索 `tag_id` 过滤是否仍可用 |
| Match Quality segments | 检查 `job_tag` 分层名称变化是否影响前后对比 |
| Public tag consumers | 检查招聘端候选人分析、企业/岗位画像、人才池、岗位详情等公共标签消费页 |

操作：

1. 管理员编辑字段。
2. 后端调用 `PUT /api/v1/base-data/tags/{tag_id}`。
3. 系统写入 operation log，action = `update`。
4. 如果变更 category 或 parent_id，验收父子关系和 public API 返回。

## 停用规则

停用不是删除。当前系统通过 `status = inactive` 隐藏 public API 输出，并保留历史引用解释能力。

### 可停用条件

[OK] 该职位/标签不再建议新增使用。
[OK] 已确认历史数据仍需要保留引用。
[OK] 已检查 active 替代项是否存在。
[OK] 已通知会使用 public API 的前端页面。

### 禁止事项

[OK] 不删除历史引用。
[OK] 不直接改历史岗位、求职意向、简历画像中的引用 id。
[OK] 不把停用项从操作日志或详情页中隐藏。
[OK] 不在缺少替代项时停用高频职位/标签。

### 停用验收

[OK] Admin 列表按 `status=inactive` 能查到。
[OK] Public API 不返回 inactive 记录。
[OK] Operation log action = `deactivate`。
[OK] 已有关联业务记录仍能显示历史名称或回退展示。

## 影响检查流程

每次 edit/deactivate 必须填写一条影响检查记录：

```text
Base Data Impact Record
- resource_type: standard_position | tag
- resource_id:
- change_type: create | update | deactivate
- changed_fields:
- affected jobs:
- affected seeker intent:
- affected structured resume profiles:
- affected search behavior:
- affected match quality segments:
- affected public consumers:
- rollback plan:
- operation_log_id:
```

影响等级：

| Level | Criteria | Action |
| --- | --- | --- |
| Low | 纯 description/color/sort_order 调整 | 可直接变更并验收日志 |
| Medium | name/aliases/category/parent 调整，影响展示或筛选 | 先记录影响检查，再变更 |
| High | 高频职位/标签停用，或影响 Match Quality 前后对比口径 | 先准备替代项和公告，必要时延后 |

## 回滚规则

| Change | Rollback |
| --- | --- |
| create | 将新增项停用，不物理删除 |
| update name/category/aliases | 按 operation log before 快照恢复 |
| update parent/color/sort | 按 operation log before 快照恢复 |
| deactivate | 重新置为 active，并记录恢复原因 |

回滚也必须产生新的 operation log，不能直接改库。

## 风险与后续

| Risk | Severity | Mitigation |
| --- | --- | --- |
| 分层名称变化导致 Match Quality 前后不可比 | P2 | 变更 category/name 前记录变更窗口和旧名称 |
| 停用高频标签导致筛选项消失 | P2 | 先准备替代标签并做 public consumers 检查 |
| 历史引用无法解释 | P2 | 保留 inactive 详情和 operation logs，不物理删除 |
| 多角色审批尚未实现 | P3 | 当前 P0 使用 admin；后续可拆 `data_operator`/`data_reviewer` |
