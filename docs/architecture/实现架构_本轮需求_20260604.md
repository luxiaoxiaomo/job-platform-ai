## 二、新增数据模型（mock/data.js）

本轮新增 14 个数据导出（不含更早就有的 `myApplications`，本轮仅为其补充了 `timeline` 字段），按业务域分组：

### 2.1 人才/候选人域

```
candidateList[]          候选人列表（B8）—— id, name, job, matchScore, tags, emotion, hasResume
  └─ getCandidate(id)

jobVisitors{jobId: []}   岗位访客（B9 浏览量穿透）—— views, lastView, matchScore, hasChatted
  └─ getJobVisitors(jobId)

talentPool[]             人才池（B12）—— matchAvg, status, appliedJobs[], lastActive, viewed
  ├─ talentStats         池总览统计
  └─ getTalent(id)

teamNotes{candidateId:[]} 团队协作备注（补3）—— author, text, time
  ├─ getTeamNotes(id)
  └─ currentRecruiter    当前操作人身份
```

**关键关系**：`candidateList` / `jobVisitors` / `talentPool` 三者描述的是**同一批人**的不同视图——
- `candidateList`：岗位维度（谁应聘了某岗位）
- `jobVisitors`：流量维度（谁浏览了某岗位）
- `talentPool`：人才维度（一个人的全貌，跨岗位聚合）

> ⚠️ 三者用的 id 取自同一命名空间（范围 1-21，缺 9），但**覆盖范围不同**：`candidateList` 含 8 人（id 1-8）、`talentPool` 含 10 人（id 1-8,10,11）、`jobVisitors` 跨岗位汇总含 18 人（id 1-21 缺 4/6/9）。三者对同一 id 指向同一个人，但并非每个列表都包含全部人。真实后端应是**一张 candidate 表 + 多个查询视图**，而非三张独立表。当前 mock 数据手动保持 id 语义一致，接真实后端时需收敛为单一数据源。

### 2.2 招聘者运营域

```
aggregateStats           全岗位聚合统计（B11）—— totalViews/UV/Msgs/Exchanges, avgMatch, topJobs[]
followUpReminders[]      跟进提醒（补4）—— reason, level(urgent/normal)
jdAttractiveness         JD 吸引力分析（补7）—— score, factors[], suggestions[], benchmark
```

> ⚠️ `aggregateStats` 必须与 `myJobs` 各岗位数据之和一致（已手动对齐：871 浏览 / 676 UV / 28 留言）。真实后端应由 `myJobs` 实时聚合计算，不应存独立的汇总数。

### 2.3 应聘者求职域

```
myApplications[]         投递记录（A8）—— status, timeline[]（5 节点状态机）
interviewPrep            AI 面试准备（A9）—— companyBrief, commonQuestions[], tips[]
```

**投递状态机**（timeline 节点）：
```
已投递 → 招聘者已查看 → 沟通中 → 邀约面试 → 面试结果
```
每节点含 `{ node, time, done }`，前端按 `done` 渲染实心/空心圆。

## 三、组件关系与状态流

### 3.1 招聘者端导航架构

```
RecruiterApp (TabBar 容器)
  ├─ tab=jobs     → JobList        ┐
  ├─ tab=talent   → TalentEntry    │ 这 4 个是「tab 内容」
  ├─ tab=messages → MsgList        │ 由 RecruiterApp 内部 useState 切换
  └─ tab=profile  → Profile        ┘
            │
            │ （以下是独立路由页面，离开 TabBar 容器）
            ▼
  RecruiterTalentPool   /recruiter/talent       ← 底部用 RecruiterBottomNav 补 TabBar
  RecruiterTalentDetail /recruiter/talent/:id
  RecruiterVisitors     /recruiter/job/visitors/:jobId
  RecruiterStats        /recruiter/stats
  RecruiterCandidate    /recruiter/candidate
```

**关键设计：双层导航**
- 主页面（`/recruiter/jobs`）内部用 `tab` state 切 4 个 tab
- 独立详情页用 `RecruiterBottomNav` 组件**模拟**同一个 TabBar
- 两者通过 URL 参数桥接：`RecruiterBottomNav` 点「消息」→ `navigate('/recruiter/jobs?tab=messages')` → `RecruiterApp` 用 `useSearchParams` 读取并 `setTab`

```
RecruiterBottomNav.onChange('messages')
   → navigate('/recruiter/jobs?tab=messages')
      → RecruiterApp: useSearchParams().get('tab')==='messages'
         → useEffect 同步 setTab('messages')
```

> ⚠️ 这是为了在纯前端 mock 下保持 TabBar 一致性的折中方案。真实小程序应使用原生 TabBar（`app.json` 配置），页面间导航不影响底部栏。

### 3.2 穿透链路（本轮核心）

招聘者从任何看到"人"的地方都能穿透到人才详情：

```
                    ┌─────────────────────────────┐
                    │   RecruiterTalentDetail      │
                    │   /recruiter/talent/:id      │
                    └──────────────▲──────────────┘
                                   │ 全部指向同一详情页
      ┌────────────────┬──────────┼──────────┬────────────────┐
      │                │          │          │                │
 JobList          RecruiterStats  │   RecruiterVisitors  RecruiterCandidate
 浏览/留言数字      4个统计数字     │   访客人名/头像      候选人卡片
 → visitors       → visitors/talent│  → talent/:id       → talent/:id
                                   │
                            RecruiterChat
                            「查看简历」→ talent/:id
```

数据穿透的 id 一致性由 mock 保证（chat.id === talent.id === visitor.id === candidate.id）。

### 3.3 应聘者投递状态流

```
SeekerApplications (投递记录)
  └─ 点卡片 → 展开 timeline[]（本地 useState expandedId）
       └─ status==='invited' → 「AI 面试准备」按钮
            └─ navigate('/seeker/interview-prep')
                 └─ SeekerInterviewPrep (读 interviewPrep mock)
```

### 3.4 全局状态：ProfileContext

唯一的跨页面状态（应聘者投递门槛 A3）：

```
ProfileProvider (包裹所有 /seeker/* 路由)
  ├─ completed   补充信息已填
  ├─ hasResume   简历已上传
  └─ unlocked = completed && hasResume

  消费方：
    SeekerJobDetail    读 unlocked 决定是否解锁完整信息+投递
    SeekerProfileEdit  markCompleted()
    SeekerResumeUpload markResume()
    ResumeUploadInline markResume()
```

> ⚠️ 这是唯一用 Context 的全局状态。其余所有页面状态都是组件内 `useState`（刷新即重置）。真实产品中这些状态都应来自后端 API。

## 六、已知技术债 / 接后端时需收敛

1. **三视图数据源未统一** —— candidateList/jobVisitors/talentPool 应收敛为单一 candidate 数据源 + 查询视图，当前靠手动保持 id 一致。

2. **聚合数据手动对齐** —— aggregateStats 与 myJobs 之和需手动同步，真实后端应实时计算。

3. **状态全在组件内** —— 除 ProfileContext 外，所有交互状态（筛选/展开/标签编辑/备注）刷新即丢，需后端持久化。

4. **TabBar 双层折中** —— RecruiterBottomNav 是 mock 下的折中，真实小程序用原生 TabBar。

5. **id 体系混用** —— chat.id / talent.id / job.id 在不同 mock 间语义不同但数值偶有重叠，接口设计时需明确各自命名空间。

6. **无分页/无加载态** —— 列表全量渲染，真实场景需分页 + 骨架屏 + 空/错误态（部分页面已有 empty 态）。

新增的可复用模式：
- **状态时间线**（投递进度）—— 可抽成 `Timeline` 组件

- **协作备注区**（作者+时间+输入）—— 可抽成 `NoteThread`

> 建议下一轮重构时把这 3 个模式抽成共享组件，减少重复。
