# P3 人岗匹配与规则配置产品化收尾

## AI 速读卡

- 产品目标：把人岗匹配从规则版计算推进到可配置、可审计、可发布、可观察的运营闭环。
- 当前状态：R-P3-01 到 R-P3-10 均已完成，P3 主线可进入产品化验收与 P4 规划。
- 已实现核心：真实匹配 API、前端真实化、规则配置落库、版本生成、版本比较/回滚、AB 实验、匹配审计、发布治理、质量看板。
- 主要用户：求职者、平台管理员；招聘者侧匹配治理入口未进入 P3。
- 关键后台页面：Match Rules、Rule AB Tests、Match Audits、Rule Releases、Match Quality。
- 关键接口：`/api/v1/matches/jobs/{job_id}/me`、`/rule-configs`、`/rule-experiments`、`/audits`、`/rule-operation-audits`、`/quality/summary`。
- P3 边界：完成规则驱动与运营治理闭环，不做向量/LLM 智能匹配、不做自动调权、不做复杂审批流。
- 下一个研发方向：Match Quality P1 或 P4 智能匹配与治理增强。

### 1.2 当前可演示能力

求职者侧：

- 求职者可以打开岗位匹配页，看到基于真实简历画像和真实岗位数据计算出的总分、等级、建议、维度得分、命中点和缺口点。
- 匹配响应会返回规则来源信息，包括 `rule_config_id`、`experiment_id`、`experiment_bucket`、`audit_id`、`scope`、`template_key`。
- 当存在运行中实验时，同一求职者和岗位组合会稳定进入 control 或 treatment 桶。

管理端：

- 管理员可以查看规则列表、规则详情、维度配置、版本历史。
- 管理员可以编辑规则并保存为新版本，而不是覆盖历史版本。
- 管理员可以比较版本差异，并通过回滚生成新版本。
- 管理员可以创建规则实验，查看 control/treatment 的匹配效果。
- 管理员可以查看匹配审计列表和单条审计详情，追踪某次匹配使用了哪套规则、哪些维度贡献了分数。
- 管理员可以在发布治理页执行发布前检查、发布规则、暂停/恢复/结束实验，并查看操作审计。
- 管理员可以在质量看板查看匹配量、平均分、高中低分布、访问/收藏/投递数量和转化率。

## 第三章：P3 范围与非范围

### 3.1 P3 已完成范围

`硬约束` P3 当前已经覆盖：

- 规则版人岗匹配真实计算。
- 匹配结果可解释，能展示权重、维度、命中、缺口和来源。
- 规则配置可落库、可读取、可 fallback。
- 规则可编辑，但通过新版本保存，保留历史。
- 多模板、多版本、版本比较、回滚生成新版本。
- AB 实验可配置，并真实影响运行时匹配。
- 匹配审计可持久化、可查询、可追踪规则来源。
- 发布前检查和发布治理可阻断明显风险。
- 运行中实验、发布动作、实验状态变化有操作审计。
- 匹配质量可以按规则版本、实验桶和日期做基础运营观察。

### 3.2 P3 明确不做范围

`硬约束` 以下能力不属于已完成 P3：

- 向量匹配、embedding 检索、语义召回。
- LLM 实时评分、LLM 生成匹配解释。
- LLM 自动生成规则、自动修改规则、自动调权。
- 招聘者自定义规则配置入口。
- 双向候选人排序、招聘者侧推荐队列。
- 长周期离线重算、批量模拟发布影响。
- Redis 或专用匹配缓存治理。
- 复杂 RBAC、多级审批、发布审批流。
- 定时发布、自动回滚、灰度自动扩缩量。
- AB 实验统计显著性、置信区间、样本量建议。
- 分岗位/城市/职位类型的质量分层分析。
- 质量异常自动告警和调权建议。

## 第四章：P3/P4 边界

### 4.1 P3 完成定义

P3 的完成标准不是“匹配算法足够智能”，而是“规则驱动的人岗匹配可以被运营维护，并且生产行为可追踪”。

P3 可以视为完成，当以下条件同时成立：

- 求职者看到的匹配结果来自真实数据和真实规则。
- 管理员可以维护规则版本，但不会破坏历史记录。
- 规则上线有最小治理能力，能阻断运行中实验冲突和非法规则。
- 每次匹配能追踪到规则版本、实验桶和维度快照。
- 运营能用质量看板观察规则版本、实验桶和行为转化的基础表现。
- 自动测试、前端构建和浏览器验收脚本存在可复跑基线。

按当前证据，P3 主线满足完成定义。

### 4.2 P4 候选方向

`推荐默认` 下一个研发阶段不建议再命名为 P3 单点补丁，而应拆为 P4 或 Match Quality P1：

1. Match Quality P1：分层质量分析、显著性、质量告警、调权建议。
2. 发布治理 P1：历史样本重算、发布影响预估、定时发布、自动回滚。
3. 权限治理 P1：rule_operator、rule_reviewer、viewer 等细分角色和审批流。
4. 智能匹配 P4：向量召回、LLM 解释、混合评分、招聘者侧候选人排序。
5. 数据运营 P4：规则效果长期留存、趋势报表、导出、跨周期对比。

## 第五章：手工验收路径

### 5.1 管理端验收

1. 启动后端和前端，进入 `/admin-ra`。
2. 打开 `Match Rules`，确认规则列表、详情、编辑、历史页可用。
3. 编辑一个非归档规则，保存为新版本，确认跳转到新版本详情。
4. 打开历史页，确认新旧版本都存在。
5. 执行版本比较，确认维度差异、权重差异可见。
6. 执行回滚，确认系统生成新版本，而不是覆盖历史版本。
7. 打开 `Rule AB Tests`，创建实验，触发求职者匹配后查看 control/treatment 效果。
8. 打开 `Match Audits`，按岗位、求职者、规则、实验、bucket 和时间过滤，打开单条详情。
9. 打开 `Rule Releases`，对候选规则执行 release-check；有 running 实验时应被阻断，暂停实验后可发布。
10. 打开 `Match Quality`，确认 KPI、规则版本表、实验桶表和日期趋势表可加载，过滤条件生效。

### 5.2 求职者侧验收

1. 使用求职者账号上传并确认简历解析结果。
2. 打开一个 active 岗位的匹配页。
3. 确认页面展示真实匹配分、等级、建议、维度得分、命中点和缺口点。
4. 收藏、访问或投递岗位。
5. 回到管理端 `Match Quality`，确认相关行为在质量指标中体现。

## 第六章：剩余缺口与风险

### 6.1 产品缺口

- 现有质量看板是 P0 运营观察，不包含统计显著性和样本量判断。
- 审计和质量数据能看事实，但尚不能自动给出规则调优建议。
- 发布治理可以检查和阻断，但没有审批工作流、定时发布和自动回滚。
- 当前权限仍以 `admin` 为主，没有拆分规则运营、审核和只读角色。
- 规则表达仍偏工程配置，没有 PM/运营友好的可视化规则 DSL。
- 质量指标依赖现有访问、收藏、投递行为，没有覆盖招聘者反馈、面试、通过/拒绝等后链路。

### 6.2 工程风险

- `docs/p3-match/P3_人岗匹配与规则配置协作计划.md` 历史内容存在编码显示异常；后续建议以本文和 `docs/HANDOFF.json` 作为 P3 收尾真相源。
- P3 浏览器脚本依赖本地服务、账号和种子数据，建议后续整理成一键验收脚本。
- react-admin 页面已经覆盖 P3 核心能力，但仍可做交互一致性和空状态打磨。
- 规则发布和实验治理目前满足 P0，复杂并发、跨 scope 策略和生产级审计报表仍需 P1/P4 规划。
