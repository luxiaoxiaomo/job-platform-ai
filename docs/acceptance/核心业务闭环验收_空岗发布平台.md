## 验收结论

本轮为 dry-run 验收，不启动前后端服务，不声明浏览器端 12 步 E2E 已通过。

当前代码已经具备真实 API-backed 的岗位发布/审核/公开列表、投递、会话消息、联系方式交换主干；前端也存在对应 service 和部分真实页面入口。但前端仍保留 mock/demo/fallback 区域，且本轮未执行一键种子数据和浏览器脚本，因此上线前必须补一次真实环境 E2E 验收。

## 分流程验收标准

### Recruiter Job Publishing

[OK] 招聘者端必须通过 `POST /api/v1/jobs/me` 创建岗位。
[OK] 内容变更后必须重新进入审核或可审核状态。
[OK] 验收记录必须保存创建 job id、创建账号、状态变化和请求时间。
[OK] 使用 mock 招聘者或本地静态岗位时，只能标为 mock-only。

### Seeker Browse/Search/Application

[OK] 求职者岗位列表和详情必须来自 `GET /api/v1/jobs/public` 与 `GET /api/v1/jobs/public/{job_id}`。
[OK] 搜索验收必须记录搜索词、返回 job id、是否命中真实后端。
[OK] 投递必须通过 `POST /api/v1/applications` 创建，并在 `GET /api/v1/applications/me` 中可见。
[OK] 如果页面 fallback 到本地 demo 数据，该步骤不得计入通过。

### Recruiter Review

[OK] 招聘者必须能通过 `GET /api/v1/applications/recruiter` 看到真实投递。
[OK] 招聘者必须能打开 `GET /api/v1/applications/recruiter/{application_id}`。
[OK] 状态处理必须通过 `POST /api/v1/applications/{application_id}/status` 留下真实状态记录。

### Communication

[OK] 留言咨询必须创建或复用真实 conversation。
[OK] 求职者和招聘者都必须能发送消息，消息刷新后仍存在。
[OK] 招聘者消息列表必须能看到求职者发起的真实 conversation。
[OK] AI 快捷回复、静态聊天记录和 mock 消息不得计入真实聊天通过证据。

### Contact Exchange

[OK] 联系方式交换必须在聊天页内完成，不在岗位详情首屏直接交换。
[OK] 请求、同意/拒绝和最终联系人展示必须来自 contact exchange API。
[OK] 同意后，招聘者端展示求职者联系方式；求职者端展示招聘者联系方式。
[OK] 刷新后仍能看到已交换联系方式。

### Status Flow

[OK] Job: draft/pending -> approved/active 或 rejected，前台只展示可见状态。
[OK] Application: submitted -> viewed/shortlisted/rejected 等招聘者处理状态必须可追踪。
[OK] Conversation: opened -> messaged -> contact_exchange_requested -> accepted/declined。
[OK] 任何状态变化都应能从真实 API 再读出，不依赖前端临时 state。
