# 空岗信息发布对接平台全链路演示文档

这份文档供现场演示人员直接使用。推荐按 20 分钟标准路线展示：招聘者完成企业认证并发布岗位，管理员完成审核，求职者上传简历、查看匹配并投递，双方沟通和交换联系方式，最后由管理员查看业务闭环、基础数据和 Match Quality 运营结果。

文档中的账号、密码和数据仅用于本地演示环境，不得用于生产环境。

## 1. 演示目标

本次演示重点回答 4 个问题：

1. 平台是否覆盖招聘者、求职者和管理员 3 类角色。
2. 岗位是否经过企业认证、发布、审核、公开、投递和处理的完整流程。
3. 简历结构化、人岗匹配、消息和联系方式交换是否由真实 API 支撑。
4. 管理端是否能看到用户、基础数据、匹配质量、异常和调优建议。

一句话开场：

> 这不是一个只展示静态页面的招聘原型。接下来会用 3 类真实账号走完从企业认证、岗位发布到求职者投递、双方建立联系，再到平台运营分析的完整链路。

## 7. 20 分钟标准演示脚本

### 第 1 阶段：平台定位，约 1 分钟

打开首页和登录页。

讲解话术：

> 平台围绕空岗信息发布和人才对接构建，包含招聘者、求职者、管理员 3 类角色。业务数据通过真实后端 API 流转，管理端负责企业和岗位审核，并对匹配质量进行持续治理。

观察点：

- 页面正常打开。
- 登录页使用真实 API。
- 不出现 Failed to fetch。

### 第 2 阶段：招聘者注册与企业认证，约 2 分钟

角色：招聘者。

页面：

- /#/login
- /#/recruiter/register

操作：

1. 使用最新 manifest 中的招聘者账号登录。
2. 进入企业认证。
3. 展示企业名称、统一社会信用代码、法人和营业执照信息。
4. 提交认证，状态进入待审核。

讲解话术：

> 招聘者不是注册后就能直接发布公开岗位。平台首先建立企业身份，认证申请进入管理员审核，避免未认证主体直接发布招聘信息。

通过标准：

- 招聘者登录后进入 /recruiter/jobs。
- 认证信息可以提交。
- 状态为 pending 或页面明确显示待审核。

### 第 3 阶段：管理员审核企业，约 1 分钟

角色：管理员。

页面：

- /#/admin
- /#/admin/company-certifications

操作：

1. 登录管理员账号。
2. 打开企业认证审核列表。
3. 找到刚才的企业。
4. 查看详情并审核通过。

讲解话术：

> 管理员能查看认证材料、主体信息和审核状态。审核通过后，招聘者才进入可持续发布岗位的业务阶段。

### 第 4 阶段：招聘者创建岗位，约 2 分钟

角色：招聘者。

页面：

- /#/recruiter/job/create
- /#/recruiter/jobs

推荐演示岗位：

| 字段 | 示例 |
| --- | --- |
| 岗位名称 | PeopleSoft HCM 实施顾问 |
| 城市 | 上海 |
| 薪资 | 18K 至 28K |
| 经验 | 3 年 |
| 学历 | 本科 |
| 技能标签 | PeopleSoft、HCM、Oracle、SQL |

操作：

1. 新建岗位。
2. 填写岗位职责、要求和福利。
3. 保存并提交审核。
4. 回到岗位列表，展示 pending 状态。

讲解话术：

> 岗位数据不是一段不可计算的文本。系统保留城市、薪资、经验、学历和技能标签等结构化字段，为搜索、标准化和人岗匹配提供输入。

### 第 5 阶段：管理员审核岗位，约 1 分钟

角色：管理员。

页面：/#/admin。

操作：

1. 打开审核管理。
2. 找到刚创建的岗位。
3. 查看企业、岗位描述和标签。
4. 审核通过。

讲解话术：

> 新岗位默认不直接公开。管理员审核通过后，状态从 pending 变为 active，求职者端才能检索和浏览。

### 第 6 阶段：求职者发现岗位，约 2 分钟

角色：求职者。

页面：

- /#/seeker/home
- /#/seeker/job/{job_id}

操作：

1. 使用最新 manifest 中的求职者账号登录。
2. 在岗位列表或搜索页找到演示岗位。
3. 打开岗位详情。
4. 展示岗位描述、技能、城市、薪资和企业信息。

讲解话术：

> 岗位审核通过后进入公开岗位池。求职者看到的是同一条真实岗位记录，不是另一份前端静态数据。

### 第 7 阶段：简历上传和结构化档案，约 2 分钟

角色：求职者。

页面：

- /#/seeker/resume
- /#/seeker/parse-history
- /#/seeker/portrait

操作：

1. 上传 docx 简历。
2. 展示解析结果或解析历史。
3. 确认姓名、学历、工作年限、期望岗位和技能。
4. 打开简历画像。

推荐样例内容：

~~~text
PeopleSoft HCM、Oracle SQL、本科学历、4 年经验、上海、期望薪资 20K 至 25K。
~~~

讲解话术：

> 简历上传后会形成结构化档案。后续匹配使用的是经过确认的学历、经验、城市和技能，而不是只依赖关键词全文搜索。

### 第 8 阶段：人岗匹配，约 2 分钟

角色：求职者。

页面：/#/seeker/match/{job_id}。

操作：

1. 从岗位详情进入匹配分析。
2. 展示匹配分、命中项、缺口和规则来源。
3. 说明本次匹配会生成 match audit。

讲解话术：

> 匹配结果不是一个无法解释的黑盒分数。系统保留使用的规则配置、各维度评分和审计 ID，管理端后续可以对质量进行回看。

重点强调：

- 匹配结果可解释。
- 规则版本可追溯。
- 匹配审计进入 Match Quality 汇总。

### 第 9 阶段：收藏与投递，约 1 分钟

角色：求职者。

页面：

- /#/seeker/job/{job_id}
- /#/seeker/applications

操作：

1. 收藏岗位。
2. 点击投递。
3. 填写简短附言。
4. 打开投递记录，确认状态为 submitted。

讲解话术：

> 投递会关联求职者、简历、岗位和招聘者。求职者端的投递记录与招聘者端的人才池读取的是同一条 application 数据。

### 第 10 阶段：招聘者查看投递，约 1 分钟

角色：招聘者。

页面：

- /#/recruiter/talent
- /#/recruiter/applications/{application_id}

操作：

1. 打开人才池。
2. 找到刚才的求职者。
3. 展示候选人简历、匹配信息和投递状态。
4. 如时间允许，演示已查看、邀面等状态流转。

讲解话术：

> 招聘者只看到与自己岗位相关的投递。候选人详情同时提供简历信息、岗位上下文和处理状态，方便形成招聘漏斗。

### 第 11 阶段：消息与联系方式交换，约 2 分钟

角色：求职者与招聘者。

页面：

- /#/seeker/chat/{conversation_id}
- /#/recruiter/chat/{conversation_id}

操作：

1. 求职者从岗位或投递进入会话。
2. 求职者发送消息。
3. 招聘者回复。
4. 求职者发起联系方式交换。
5. 招聘者接受。
6. 双方重新打开会话，确认联系方式交换状态为 accepted。

讲解话术：

> 平台内沟通和联系方式交换是两个阶段。双方先在站内沟通，只有一方申请且另一方同意后，结构化联系方式才向双方可见，过程可审计。

### 第 12 阶段：业务闭环和 Match Quality，约 3 分钟

角色：管理员。

页面：

- /#/admin
- /#/admin-ra/match-quality

先展示业务闭环指标：

- 成功对接数。
- 投递总数和状态分布。
- 联系方式交换状态。

再展示 RP401 Match Quality 稳定数据：

| 指标 | 当前稳定样例 |
| --- | ---: |
| 匹配样本 | 240 |
| 平均分 | 84 |
| 高分样本 | 200 |
| 低分样本 | 40 |
| 收藏率 | 50% |
| 投递率 | 50% |
| 低分率 | 16.67% |
| 异常 | 至少 2 条 |
| 调优建议 | 至少 2 条 |
| 实验结论 | treatment_likely_better |

操作：

1. 打开 Match Quality。
2. 展示整体样本和高、中、低分分层。
3. 按城市筛选 RP401-Shanghai。
4. 展示低分异常和调优建议。
5. 展示实验对照组、实验组和决策提示。

讲解话术：

> 平台不仅完成匹配，还把匹配结果和后续行为重新汇总。运营人员可以看到低分率、投递率、异常城市和实验差异，从而决定是否调整规则，而不是只关注模型离线分数。

## 10. 常见故障和现场兜底

### 10.1 页面显示 Failed to fetch

按顺序检查：

~~~powershell
curl.exe -s http://127.0.0.1:8003/health
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:5174/
netstat -ano | Select-String ':5174|:8003'
~~~

处理方式：

1. 后端 8003 不在线：重新启动 uvicorn。
2. 前端 5174 不在线：重新运行 npm.cmd run dev。
3. 两端都在线：强制刷新浏览器。
4. 账号切换异常：清理 Local Storage 后重新登录。

### 10.2 登录返回 401

- 优先使用本文固定账号或最新 manifest 账号。
- 检查是否把招聘者密码和求职者密码混用。
- 不要继续使用历史文档中已经失效的随机账号。

### 10.3 用户手机号显示“手机号不可用”

这是历史密文使用旧密钥造成的单行降级，不影响用户列表、角色筛选和核心业务演示。不要现场修改或猜测历史手机号。

### 10.4 求职者无法投递

检查：

1. 是否已经上传并确认简历。
2. 岗位是否为 active。
3. 是否已经投递过同一岗位。

兜底方式：使用最新 12 步脚本生成的 application_id 和 manifest 继续后半段演示。

### 10.5 Match Quality 没有数据

重新执行：

~~~powershell
cd D:\AIposition\backend\job-platform
.\.venv\Scripts\python.exe scripts\seed_rp401_demo.py

cd D:\AIposition
$env:API_BASE_URL='http://127.0.0.1:8003'
$env:APP_BASE_URL='http://127.0.0.1:5174'
node frontend\wechat-prototype\output\playwright\manual-rp401-demo-acceptance.cjs
~~~

### 10.6 页面操作临时不稳定

按以下优先级兜底：

1. 使用页面刷新或重新登录。
2. 使用 Swagger 展示同一真实 API。
3. 打开最新 12 步 manifest 展示账号、对象 ID 和步骤结果。
4. 展示 output/playwright 下的验收截图。

不要把 mock-only 页面或静态数字描述为真实业务结果。

## 12. 演示边界

现场必须如实说明：

1. 当前环境是本地或专用 demo 环境，不是生产环境。
2. RP401 seed 用于稳定展示 Match Quality，不等同于完整业务闭环证据。
3. 完整业务闭环证据来自 manual-live-12-step-e2e.cjs 生成的 manifest。
4. 部分页面仍可能包含 mock 或 fallback 展示，不能作为真实 API 证据。
5. 外部向量服务、生产密钥、生产流量和真实灰度发布不在本次演示结论内。

> 今天演示的是本地真实 API 和数据库支撑的业务闭环，以及稳定种子数据支撑的匹配质量运营能力。生产部署、外部向量服务和真实流量实验需要独立验收。

## 14. 一页速记话术

~~~text
1. 招聘者先完成企业认证，平台确认发布主体。
2. 招聘者创建结构化岗位，管理员审核后岗位才公开。
3. 求职者上传简历并确认结构化档案。
4. 系统根据技能、经验、学历、城市等维度生成人岗匹配和审计记录。
5. 求职者收藏并投递，招聘者在人才池看到同一条真实投递。
6. 双方在站内沟通，经双方同意后交换联系方式。
7. 管理端重新汇总成功对接和匹配质量，识别异常并给出调优建议。
~~~

最终收口话术：

> 这条链路把“能发布岗位”推进到了“能够安全发布、精准匹配、有效对接并持续治理”。前台的每一次匹配和投递，都能在后台形成可追踪、可分析、可优化的数据闭环。
