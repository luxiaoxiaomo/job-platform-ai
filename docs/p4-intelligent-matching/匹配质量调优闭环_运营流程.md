# 匹配质量调优闭环运营流程

Date: 2026-06-23
Scope: Match Quality P1 evidence -> rule draft -> experiment -> release governance -> before/after quality comparison
Primary users: 平台管理员、规则运营
System role: P0 继续使用 `admin`

## 目标

把 Match Quality 从“看指标”推进到“可审计的运营调优闭环”：

1. 从 `Segments`、`Anomalies`、`Tuning Suggestions` 定位质量问题。
2. 把建议转成需要人工确认的规则编辑草稿。
3. 通过规则实验验证 control/treatment 差异。
4. 通过 release-check 和操作审计完成发布治理。
5. 发布后用同一套 Match Quality 指标做前后质量对比。

本流程不引入向量召回、LLM 自动调权、自动发布、自动回滚或多角色审批流。P4 智能匹配可以复用本流程作为质量治理底座，但不能绕过本流程直接改线上规则。

## 现有系统证据

| Capability | Current Evidence | Operational Use |
| --- | --- | --- |
| Match Quality summary | `GET /api/v1/matches/quality/summary` | 读取 summary、segments、experiment_confidence、anomalies、tuning_suggestions |
| Match Quality UI | `/admin-ra/match-quality`, `frontend/wechat-prototype/src/admin-ra/resources/match-quality/dashboard.jsx` | 筛选规则版本、实验、城市、职位类目、标准职位、岗位标签和时间范围 |
| Match Audits | `GET /api/v1/matches/audits`, `GET /api/v1/matches/audits/{audit_id}` | 钻取异常样本，核对维度快照和打分证据 |
| Rule configs | `/api/v1/matches/rule-configs` and `/versions` | 从现有规则创建 draft/testing 版本 |
| Rule compare/rollback | `/compare/{target_config_id}`, `/rollback` | 比较版本差异，必要时创建回滚版本 |
| Rule experiments | `/api/v1/matches/rule-experiments`, `/effects`, `/status` | 创建灰度/AB 实验，查看 control/treatment 效果，暂停/恢复/结束实验 |
| Release governance | `/api/v1/matches/rule-configs/{id}/release-check`, `/publish` | 发布前检查 blocker/warning，要求 warnings 显式确认 |
| Operation audits | `/api/v1/matches/rule-operation-audits` | 查看发布、实验状态变更和阻断发布记录 |

## 输入信号

### Segments

用于定位“哪类样本表现异常”。运营必须优先关注：

| Field | Use |
| --- | --- |
| `segment_type` / `segment_label` | 城市、职位类目、标准职位、岗位标签、规则版本或实验桶 |
| `match_count` / `sample_status` | 判断样本是否足够；`insufficient` 不允许形成强结论 |
| `avg_score` / `low_score_rate` | 判断规则打分分布 |
| `application_rate` / `application_rate_delta` | 判断下游投递转化是否弱于全局 |
| `risk_level` | 排查优先级 |

### Anomalies

用于形成待排查问题单，而不是直接形成规则变更。

| Anomaly | First Action |
| --- | --- |
| `low_application_rate` | 打开同一分层的 Match Audits，核对高分样本是否岗位吸引力不足、薪资偏低或技能匹配过宽 |
| `high_low_score_rate` | 检查该分层是否被过度过滤，必要时考虑 broadening logic 或独立 scoped rule |
| `high_score_low_conversion` | 排查假阳性，优先检查 skill、salary、city、experience 维度 |

### Tuning Suggestions

建议只能作为草案。每条建议必须显示并遵守 guardrail：

```text
仅生成建议草案，不自动修改规则；请通过规则编辑页创建新版本并走发布治理。
```

建议类型与处理方式：

| suggestion_type | Operational Meaning | Allowed Next Step |
| --- | --- | --- |
| `lower_weight` | 某维度可能过度放大，导致高分低转化 | 人工创建 draft/testing 规则版本并降低该维度权重 |
| `raise_weight` | 某维度可能被低估，导致低分但有转化 | 人工创建 draft/testing 规则版本并提高该维度权重 |
| `narrow_logic` | 命中逻辑过宽，可能产生假阳性 | 人工调整逻辑 JSON 或关键词集合 |
| `broaden_logic` | 命中逻辑过窄，可能产生假阴性 | 人工扩展逻辑或建立 scoped rule |
| `review_dimension` | 证据不足以指向权重变化 | 先钻取 Match Audits，不允许直接改权重 |
| `run_experiment` | 变化风险或影响面较大 | 创建实验，不直接发布 |

## 闭环流程

### Phase 1: 发现问题

1. 管理员打开 `/admin-ra/match-quality`。
2. 默认查看最近 14 天全局指标。
3. 按 `risk_level`、`application_rate_delta`、`low_score_rate`、`match_count` 排序。
4. 只把 `sample_status = limited/usable` 的异常列入待处理；`insufficient` 只记录观察。
5. 对高优先级异常打开 Match Audits，抽查至少 10 条样本或全部样本中较小者。

输出：

```text
Quality Issue Record
- rule_config_id / experiment_id
- segment_type / segment_key / segment_label
- sample_status and match_count
- anomaly type and severity
- evidence from Match Quality
- sampled audit ids
- suspected dimension
- decision: observe / draft rule / run experiment / no action
```

### Phase 2: 形成规则草案

只有在以下条件同时满足时，才允许创建规则草稿：

[OK] Match Quality 中有 `limited` 或 `usable` 样本。
[OK] Match Audits 抽查支持该维度确实可能造成误判。
[OK] 变更范围、目标指标、回滚方式已写入 Quality Issue Record。
[OK] 运营人员明确知道 Tuning Suggestion 不是自动调权结论。

操作步骤：

1. 打开对应规则版本详情或规则编辑页。
2. 基于当前 active 规则创建 `draft` 或 `testing` 新版本。
3. 只改本次问题对应的最小维度，避免一次混合多个假设。
4. 在规则描述中写入来源：`Match Quality issue: <segment>/<anomaly>/<date range>`。
5. 使用规则 compare 核对新旧差异。

禁止：

[OK] 不允许从 Tuning Suggestions 直接调用 `/versions`。
[OK] 不允许自动创建 draft/testing 版本。
[OK] 不允许绕过人工输入 reason。
[OK] 不允许一次性修改多个无共同证据的维度。

### Phase 3: 实验验证

适用条件：

| Condition | Required Action |
| --- | --- |
| 权重变化大、影响全局 scope | 必须创建 rule experiment |
| 涉及城市/职位类目/标准职位特定问题 | 优先创建 scoped rule 或小流量 experiment |
| 样本 `limited` 但业务风险高 | 先观察或小流量 experiment，不直接发布 |
| `insufficient` | 不创建实验，扩大时间范围或补充样本 |

操作步骤：

1. 创建 experiment，control 指向当前 active 规则，treatment 指向 testing 规则。
2. 设置合理流量比例，默认低流量起步。
3. 记录 experiment id、control_config_id、treatment_config_id、traffic_percent、audience。
4. 实验期间在 Match Quality 中按 `experiment_id` 查看 control/treatment。
5. 使用 Experiment Confidence 判断：
   - `insufficient_sample`: 继续观察或扩大样本，不做发布判断。
   - `treatment_likely_better`: 可以准备 release-check。
   - `treatment_likely_worse`: 暂停或结束实验，保留证据。
   - `no_clear_difference`: 继续观察、调整假设或放弃。

Guardrail:

[OK] 实验状态变化必须通过 `/api/v1/matches/rule-experiments/{experiment_id}/status`。
[OK] 同一 scope/template 不允许多个 running experiment 冲突。
[OK] 实验结论必须引用 Match Quality 的 sample_status 和 decision_hint。

### Phase 4: 发布治理

发布前必须完成：

1. 结束或暂停同 scope/template 的 running experiment，避免 release-check blocker。
2. 执行 `GET /api/v1/matches/rule-configs/{config_id}/release-check`。
3. 若存在 blockers，停止发布并记录阻断原因。
4. 若存在 warnings，必须由管理员显式确认 `confirm_warnings` 并填写 reason。
5. 调用 publish 后，检查 operation audit 中存在 `publish_rule` 或 `block_publish` 记录。

发布禁止项：

[OK] 不允许未跑 release-check 直接发布。
[OK] 不允许 blockers 存在时发布。
[OK] 不允许 warnings 未确认时发布。
[OK] 不允许建议草案直接触发发布。
[OK] 不允许自动回滚；回滚也必须创建新版本并走发布治理。

### Phase 5: 前后质量对比

发布后至少记录两个窗口：

| Window | Purpose |
| --- | --- |
| Before | active 旧版本或 experiment control 的质量基线 |
| After | 新 active 版本发布后的质量指标 |

对比指标：

[OK] `match_count`
[OK] `avg_score`
[OK] `low_score_rate`
[OK] `application_rate`
[OK] `application_rate_delta`
[OK] `segments` top risks
[OK] `anomalies` count/severity
[OK] `tuning_suggestions` 是否减少或转移

判定规则：

| Result | Criteria | Next Step |
| --- | --- | --- |
| Keep | 样本 usable，核心目标指标改善，未引入新的 high anomaly | 保持发布，记录结论 |
| Observe | 样本 limited 或改善未达阈值但无明显恶化 | 延长观察窗口 |
| Repair | 新版本出现 high anomaly 或 treatment_likely_worse | 创建修复草稿或回滚版本 |
| Roll back candidate | 核心链路明显恶化且 release window 内复现 | 创建 rollback 版本，走 release-check/publish |

## 审批与角色规则

P0 仍使用 `admin` 角色，但运营流程上必须区分职责：

| Responsibility | P0 Actor | Required Evidence |
| --- | --- | --- |
| 问题发现 | admin | Match Quality filter + segment/anomaly/suggestion evidence |
| 草稿创建 | admin | Quality Issue Record + rule compare |
| 实验启动/暂停/结束 | admin | experiment id + status operation audit |
| 发布确认 | admin | release-check result + publish reason |
| 复盘 | admin | before/after Match Quality comparison |

P1/P4 可拆分 `rule_operator` 和 `rule_reviewer`，但在当前系统未实现前，不把多角色审批作为 P0 验收阻塞项。

## 数据与审计要求

每一次闭环必须能追溯：

[OK] Match Quality 筛选条件。
[OK] Segment/anomaly/suggestion 原始证据。
[OK] Match audit sample ids。
[OK] 规则版本 diff 或 compare 结果。
[OK] Experiment id 和 status 变化。
[OK] Release-check blockers/warnings。
[OK] Publish/blocked operation audit。
[OK] Before/after comparison window。

## 空状态与异常处理

| Case | Required Behavior |
| --- | --- |
| No segment data | 显示无分层数据，不创建调优任务 |
| `sample_status = insufficient` | 只观察，不给强结论，不创建规则草稿 |
| No behavior data | 展示匹配指标，转化指标标 0，并提示行为延迟 |
| Missing standard position/tag | 归入 `Unclassified`，不得丢弃样本 |
| Only one experiment bucket | Experiment Confidence 为 `not_applicable`，检查流量或样本 |
| API failure | 不返回半真半假的建议；保留筛选条件并重试 |
