# 结构化简历解析方案讨论稿

这份文档用于 Codex 和 Claude 对齐 P2 的设计边界。核心目标不是马上做完整简历筛选，而是把“结构化提示词 -> 结构化 JSON -> 核心明细表”的链路设计清楚，避免后面 OCR、LLM、RAG 接入时返工。

## 结论

P2 采用双轨落库：

```text
resume_extracted_texts / resume_chunks
  -> 结构化解析提示词
  -> LLM 输出 structured_json
  -> JSON Schema 校验
  -> resume_structured_profiles
  -> 置信度/人工确认
  -> 核心明细表
```

`resume_structured_profiles` 是 AI 解析源结果；核心明细表是后续筛选、统计、匹配使用的业务投影。

## 设计目标

1. 结构化提示词可配置，不写死在代码里。
2. LLM 输出必须是固定 JSON，不允许自由文本。
3. JSON 必须经过后端 schema 校验和规则校验。
4. AI 结果不能直接覆盖 `seeker_profiles`。
5. 高置信度或用户确认后的字段才能投影到核心明细表。
6. 每条结构化结果和明细记录都必须追溯到 `upload_id`、`parse_run_id`、`prompt_config_id`、`prompt_version`。

## 提示词场景

在 `ai_prompt_configs` 中新增或启用以下场景：

| scenario_key | 用途 | P2 是否必须 |
| --- | --- | --- |
| `resume_structured_parse` | 从简历原文解析结构化 JSON | 必须 |
| `resume_structured_repair` | 修复不合法 JSON 或补齐缺失字段 | 可选 |
| `resume_field_confidence` | 单独评估字段置信度 | 可选 |
| `resume_tag_extract` | 提取标签 | P3 |
| `resume_keyword_extract` | 提取关键词 | P3 |

P2 先只要求 `resume_structured_parse`。

## 提示词输入变量

建议模板变量：

```text
{{resume_text}}
{{chunks}}
{{schema_json}}
{{candidate_context}}
{{rules}}
```

说明：

- `resume_text`: 原文抽取结果，必要时截断。
- `chunks`: P1 生成的 chunk 列表，可只传前 N 个或按章节传。
- `schema_json`: 后端定义的输出 JSON Schema。
- `candidate_context`: 已知账号信息，比如手机号、当前城市、求职者已确认资料。
- `rules`: 解析约束，比如不要编造、缺失填 null、保留原文证据。

## 新增表建议

### `resume_structured_profiles`

保存 LLM 或规则解析后的完整 JSON。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | ID |
| `seeker_id` | int | 求职者 |
| `upload_id` | int | 上传记录 |
| `parse_run_id` | int | 解析任务 |
| `prompt_config_id` | int | 提示词配置 |
| `prompt_version` | int | 提示词版本 |
| `schema_version` | string | 输出 schema 版本 |
| `status` | string | `draft/validated/needs_review/confirmed/rejected` |
| `structured_json` | json | 完整解析结果 |
| `validation_errors` | json | schema 或规则校验错误 |
| `model_provider` | string | 模型供应商 |
| `model_name` | string | 模型名 |
| `created_at` | datetime | 创建时间 |
| `updated_at` | datetime | 更新时间 |

### 核心明细表

P2 同步建设这些表，但允许字段先少量写入：

- `resume_basic_infos`
- `resume_educations`
- `resume_work_experiences`
- `resume_projects`
- `resume_skills`
- `resume_certificates`

每张明细表都必须包含：

```text
id
seeker_id
upload_id
parse_run_id
structured_profile_id
source
confidence_score
raw_text
source_json
created_at
updated_at
```

`source` 取值：

```text
llm / rule / ocr / manual
```

## 投影规则

JSON 到明细表不是无条件写入。

建议规则：

```text
字段置信度 >= 0.85 -> 自动投影
字段置信度 0.60 - 0.85 -> 待确认，可展示但不作为强筛选依据
字段置信度 < 0.60 -> 留在 structured_json，不投影
用户手动确认 -> 投影，不受置信度限制
```

特殊规则：

- 手机、邮箱优先相信规则抽取。
- 学历必须经过枚举归一化，比如 `本科/硕士/博士/大专/高中及以下`。
- 工作年限优先用工作经历时间段计算；LLM 给出的年限只能作为参考。
- 技能要做标准化，后续接技能字典。
- 低质量 OCR 文本默认 `needs_review`。

## 状态流转

```text
parse_run.succeeded
  -> structured_profile.draft
  -> schema 校验
  -> validated / needs_review
  -> 用户确认
  -> confirmed
  -> 投影到核心明细表
```

失败处理：

```text
LLM 输出不是合法 JSON
  -> structured_profile.needs_review
  -> validation_errors 记录原因
  -> parse_run.completed_with_errors
```

## API 草案

```http
POST /api/v1/resumes/me/parse-runs/{parse_run_id}/structured-parse
```

触发结构化解析。P2 可以同步执行，后续可切异步。

```http
GET /api/v1/resumes/me/structured-profiles/{structured_profile_id}
```

查看结构化解析结果。

```http
PUT /api/v1/resumes/me/structured-profiles/{structured_profile_id}
```

用户修改结构化字段。

```http
POST /api/v1/resumes/me/structured-profiles/{structured_profile_id}/confirm
```

确认并投影到核心明细表，同时按规则回写 `seeker_profiles`。

## 前端确认页

Claude 侧建议页面结构：

```text
左侧：原文预览 / chunk
右侧：结构化字段表单
顶部：解析状态、置信度、提示词版本
底部：确认按钮、重新解析按钮
```

字段级展示：

- 高置信度：正常显示。
- 中置信度：提示需确认。
- 低置信度：默认折叠或标红。
- 与规则冲突：明确提示冲突来源。

## 后端实现边界

Codex 负责：

1. Alembic 迁移。
2. `resume_structured_profiles` 和核心明细表模型。
3. JSON Schema 定义和校验。
4. 结构化解析 service。
5. JSON 到明细表的投影逻辑。
6. 确认后回写 `seeker_profiles`。
7. 后端测试。

Claude 负责：

1. 评审字段是否够前端使用。
2. 做结构化确认页。
3. 做字段置信度展示。
4. 做手动编辑和确认交互。
5. 浏览器联调。

## 需要 Claude 重点评审的问题

1. 前端确认页是否需要一次展示所有字段，还是分 tab 展示基础信息、教育、工作、项目、技能。
2. `confidence` 是字段级更好，还是模块级先够用。
3. `evidence` 是否需要在 P2 显示，还是只存后端。
4. `resume_basic_infos` 是否应该只保存当前确认版本，还是按 `parse_run_id` 保留多版本。
5. 用户修改结构化字段后，是立即保存草稿，还是确认时一次提交。
6. 字段冲突时前端文案如何表达，避免用户以为 AI 已经完全正确。

## 暂不做

P2 暂不做：

- 标签和关键词抽取。
- 人岗匹配评分。
- embedding。
- PDF/image OCR。
- 岗位 JD 结构化解析。
- 复杂技能字典治理。

这些进入 P3/P4，避免 P2 失控。

## 建议决策

P2 先做一个可运行闭环：

```text
docx 原文
  -> 结构化提示词
  -> structured_json
  -> schema 校验
  -> 用户确认
  -> basic/education/work/project/skill/certificate 明细表
```

这个闭环完成后，再接 OCR、标签、关键词和匹配，不会推翻结构。
