# P4 智能匹配原型设计与落地方案

## 1. 设计定位

本方案补的是 P4 智能匹配从 PRD 到工程实现之间的原型层。它不重写 `P4_智能匹配_MVP_PRD.md`，也不替代接口契约和任务包。它回答一个更具体的问题：产品页面怎么长、用户怎么操作、每一步依赖哪些字段、失败时如何降级、后续代码从哪里切入。

P4 的第一阶段应该先让平台管理员能看清智能匹配策略是否值得灰度，而不是直接把智能排序推给招聘方或求职者。现有系统已经有规则匹配、规则实验、匹配审计和 Match Quality；原型设计必须复用这些入口。

## 2. 当前基线

现有 react-admin 后台入口：

| 入口 | 当前用途 | P4 处理方式 |
| --- | --- | --- |
| `Match Rules` | 规则配置、版本、发布、对比 | 作为智能策略的 base rule 选择来源 |
| `Rule AB Tests` | 规则实验和 bucket 效果 | 扩展为智能策略灰度入口，但不破坏现有规则实验 |
| `Match Audits` | 单次匹配审计和维度快照 | 扩展智能字段、降级原因、召回来源、分数组件 |
| `Match Quality` | 分层质量、异常、调优建议 | 增加 strategy、match_source、degrade_rate、vector_recall_coverage 观察 |

现有微信端入口：

| 入口 | 当前用途 | P4 处理方式 |
| --- | --- | --- |
| 求职者岗位详情 / AI 人岗匹配分析 | 查看本人和岗位的规则匹配分、维度、亮点、缺口 | 可展示智能字段，但必须保留规则 baseline 和降级说明 |
| 招聘方投递详情 / AI 匹配分 | 查看候选人与岗位的匹配结果 | P0 不开启候选人智能排序；只允许在单个投递详情里展示可审计说明 |
| 招聘方候选人列表 / 人才库 | 列表和部分 mock/demo 匹配展示 | P0 不把智能策略作为默认排序依据 |

## 3. MVP 边界

### 3.1 P0 必做

- 后台新增 `Intelligent Matching` 菜单或二级入口。
- 管理员能创建和查看智能匹配策略草稿。
- 管理员能运行离线评估并查看 baseline vs hybrid 的报告。
- 管理员能从评估报告进入灰度实验准备，但只有通过评估门槛的策略可进入 testing。
- 匹配审计能展示智能策略字段、分数组件和降级原因。
- Match Quality 能按策略、来源、bucket、降级状态观察质量。
- 求职者和招聘方展示只作为受控说明，不改变默认生产排序。

### 3.2 P0 不做

- 不做 LLM 实时评分。
- 不做 LLM 自动改规则。
- 不做智能策略自动发布或自动回滚。
- 不让招聘方候选人列表默认按智能策略重排。
- 不把 demo/mock 评估作为上线证据。
- 不绕过 P3 的规则实验、发布治理和审计。

### 3.3 延后项

- 招聘方候选人推荐排序。
- 求职者首页智能推荐流改版。
- 自然语言解释生成。
- 自动权重学习。
- 独立算法运营角色和审批流。
- 大规模向量索引运维后台。

## 4. 信息架构

P4 后台建议在 react-admin 中增加一个菜单：`Intelligent Matching`。

一级页面：

1. `Strategies`：策略列表、状态、最近评估、最近实验。
2. `Strategy Detail`：策略参数、base rule、权重、召回配置、状态流转。
3. `Evaluation Report`：离线评估报告，比较 baseline 与 hybrid。
4. `Audit Detail Extension`：复用 `Match Audits`，展示智能字段。
5. `Match Quality Extension`：复用 `Match Quality`，增加智能维度过滤和指标。

建议路由：

```text
/admin-ra/intelligent-matching/strategies
/admin-ra/intelligent-matching/strategies/:id
/admin-ra/intelligent-matching/strategies/:id/edit
/admin-ra/intelligent-matching/evaluations/:id
/admin-ra/match-audits?strategy_id=&match_source=&degrade_reason=
/admin-ra/match-quality?strategy_id=&match_source=&experiment_bucket=
```

## 5. 关键流程

### 5.1 管理员创建策略草稿

目标：管理员基于已有规则版本创建一个可评估的智能策略。

流程：

1. 进入 `Intelligent Matching / Strategies`。
2. 点击 `Create Draft`。
3. 选择 base rule。
4. 配置 vector recall：enabled、top_n、min_similarity、candidate_source。
5. 配置 hybrid weights：rule_score、vector_score、profile_coverage_score、behavior_quality_score。
6. 保存为 `draft`。

页面反馈：

- 权重合计不等于 1.0 时阻止保存。
- base rule 不存在或 archived 时阻止保存。
- vector recall 不可用时允许保存草稿，但显示不能进入 testing 的原因。
- 保存后写入操作审计。

### 5.2 管理员运行离线评估

目标：先用样本证明 hybrid 策略比 baseline 值得灰度。

流程：

1. 在策略详情点击 `Run Offline Evaluation`。
2. 选择 sample set 或时间范围。
3. 系统校验 sample_source_distribution。
4. 生成 baseline 与 hybrid 对比报告。
5. 如果样本不足，报告标记为 `insufficient_sample`；如果样本主要来自 demo/mock，报告标记为 `demo_only`，并在证据边界区说明不可作为上线证据。
6. 如果满足门槛，允许点击 `Prepare Gray Experiment`。

报告必须显示：

- sample_count
- sample_source_distribution
- baseline avg_score、low_score_rate、application_proxy_rate
- hybrid avg_score、low_score_rate、application_proxy_rate
- vector_recall_coverage
- recall_delta
- degrade_rate
- offline_win_rate
- decision_status
- risk_notes

### 5.3 管理员准备灰度实验

目标：复用现有 Rule AB Tests，不另建一套实验治理。

流程：

1. 从评估报告点击 `Prepare Gray Experiment`。
2. control 固定为当前 active rule baseline。
3. treatment 绑定 intelligent strategy。
4. traffic_percent 初始建议不超过 10%。
5. 创建后进入 `Rule AB Tests` 观察。

约束：

- 只有 `testing` 策略可绑定 treatment。
- 样本不足、demo-only 报告、vector 服务不可用时不能创建线上灰度。
- 实验运行中所有 treatment 结果必须写入 match audit。

### 5.4 管理员查看审计解释

目标：任何一个智能结果都能解释来源，而不是只给一个分数。

在 `Match Audits` detail 中新增 `Intelligent Matching` 区块：

| 字段 | 说明 |
| --- | --- |
| match_source | `rule_baseline`、`vector_recall`、`hybrid` |
| strategy_id | 智能策略 ID |
| strategy_status | 运行时策略状态 |
| rule_score | 规则分 |
| vector_score | 语义分 |
| profile_coverage_score | 画像覆盖分 |
| behavior_quality_score | 行为质量参考分 |
| hybrid_score | 混合总分 |
| component_weights | 本次计算权重 |
| recall_source | 召回来源 |
| vector_index_version | 向量索引版本 |
| degrade_reason | 降级原因 |

展示原则：

- 如果是旧审计或纯规则匹配，显示 `Rule baseline only`。
- 如果智能字段缺失，显示 `Unknown`，不能覆盖原规则审计。
- 如果发生降级，优先展示降级原因，再展示回退后的规则结果。

### 5.5 管理员观察 Match Quality

目标：看智能策略是否真的改善质量，而不是只看离线分数。

`Match Quality` 增加过滤项：

- Strategy ID
- Match Source
- Degrade Reason
- Vector Recall Coverage range
- Experiment Bucket

新增 KPI：

- Hybrid Avg Score
- Baseline Avg Score
- Vector Recall Coverage
- Degrade Rate
- Treatment Low Score Rate
- Control Low Score Rate
- Application Rate Delta

新增表格维度：

- strategy_id
- match_source
- degrade_reason
- vector_index_version
- experiment_bucket

异常提示：

- treatment 比 control 低分率更高。
- degrade_rate 高于阈值。
- vector_recall_coverage 低于阈值。
- seeded_demo/mock_only 样本被误用于上线判断。

## 6. 求职者与招聘方展示边界

### 6.1 求职者侧

现有 `AI 人岗匹配分析` 可扩展显示智能解释，但 P0 必须保守。

允许展示：

- 当前岗位匹配总分。
- 规则维度得分。
- 如果命中 hybrid，可显示 `智能策略辅助分析` 标签。
- 匹配亮点和缺口。
- 画像不完整提醒。
- 降级说明，例如 `当前按规则匹配展示`。

不允许展示：

- 后台策略参数。
- vector index 细节。
- 实验 bucket。
- 不可审计的自然语言结论。
- 把 demo/mock 推荐说成正式推荐。

### 6.2 招聘方侧

现有投递详情里的 AI 匹配分可作为单人选解释入口。P0 不改候选人列表排序。

允许展示：

- 单个投递的匹配分。
- 维度分、亮点、缺口。
- 是否来自规则 baseline 或 hybrid。
- 需要补充的信息。

不允许展示：

- 默认把候选人列表按智能策略重排。
- 使用不可解释分数影响候选人状态。
- 自动发起邀约、淘汰或推荐。

## 7. 页面设计

### 7.1 Strategies 列表页

入口：`/admin-ra/intelligent-matching/strategies`

目标用户：平台管理员。

主要模块：

1. 顶部过滤区：Status、Base Rule、Vector Enabled、Last Evaluation Status。
2. 策略表格：ID、Name、Status、Base Rule、Weights、Vector Recall、Last Evaluation、Last Experiment、Updated At。
3. 行内动作：Open、Edit Draft、Run Evaluation、Clone、Archive。
4. 顶部动作：Create Draft、Refresh。

状态规则：

| 状态 | 可编辑 | 可评估 | 可灰度 | 可归档 | 说明 |
| --- | --- | --- | --- | --- | --- |
| draft | 是 | 是 | 否 | 是 | 初始草稿 |
| evaluating | 是 | 是 | 否 | 是 | 有评估记录但未进 testing |
| testing | 否 | 是 | 是 | 是 | 可被实验 treatment 引用 |
| active | 否 | 是 | 视治理而定 | 是 | P0 不要求 |
| archived | 否 | 否 | 否 | 否 | 历史只读 |

空状态：

- 文案：`No intelligent strategies yet.`
- 行动：`Create Draft`

错误状态：

- 403：显示无权限。
- API 不可用：保留页面结构，显示加载失败和重试。

### 7.2 Strategy Detail / Edit

入口：`/admin-ra/intelligent-matching/strategies/:id`

模块：

1. Summary：Name、Status、Base Rule、Created By、Updated At。
2. Vector Recall：enabled、top_n、min_similarity、candidate_source、index_version。
3. Hybrid Weights：rule_score、vector_score、profile_coverage_score、behavior_quality_score。
4. Fallback Policy：P0 固定 `rule_baseline`。
5. Evaluation History：最近评估报告。
6. Experiment Links：关联灰度实验。
7. Operation Audit：创建、更新、克隆、评估、归档记录。

编辑规则：

- draft/evaluating 可编辑。
- testing/active/archived 只读。
- testing/active 如需修改，必须 clone 新草稿。

### 7.3 Evaluation Report

入口：`/admin-ra/intelligent-matching/evaluations/:id`

模块：

1. Report Header：strategy、sample set、sample_count、decision_status。
2. Evidence Boundary：real_behavior、manual_review、seeded_demo、mock_only 占比。
3. Baseline vs Hybrid KPI。
4. Recall Analysis：recall_delta、vector_recall_coverage、new candidates count。
5. Degradation：degrade_rate、degrade_reason distribution。
6. Risk Notes。
7. Actions：Export Evidence、Open Audits、Prepare Gray Experiment。

决策提示：

| decision_status | 页面表现 | 允许动作 |
| --- | --- | --- |
| eligible_for_gray | 绿色标签 | 可准备灰度 |
| insufficient_sample | 黄色标签 | 不可灰度 |
| demo_only | 黄色标签 | 仅演示，不可上线 |
| hybrid_worse | 红色标签 | 不可灰度 |
| vector_unavailable | 红色标签 | 不可灰度 |

### 7.4 Match Audits 扩展

现有页面保留，新增过滤项和 detail 区块。

新增过滤项：

- Strategy ID
- Match Source
- Degrade Reason

列表新增列：

- Source

详情新增区块：

### 7.5 Match Quality 扩展

现有页面保留，新增智能过滤和 KPI。

新增过滤项：

- Strategy ID
- Match Source
- Degrade Reason

新增 KPI 卡：

- Hybrid Avg Score
- Vector Coverage
- Degrade Rate
- Control vs Treatment Delta

新增提示：

- 行为数据可能滞后。
- 灰度样本不足时不做强结论。
- demo/mock 样本不能作为上线证据。

## 10. 验收路径

### 10.1 原型验收

1. 管理员打开 `Intelligent Matching / Strategies`。
2. 创建一个 draft 策略。
3. 输入非法权重，页面阻止保存。
4. 输入合法权重，保存成功。
5. 从策略详情运行 offline evaluation。
6. 评估报告显示 sample source distribution 和 baseline/hybrid 对比。
7. demo_only 或 insufficient_sample 报告不能进入灰度。
8. eligible_for_gray 报告可以准备灰度实验。
9. `Match Audits` 可按 strategy_id 和 match_source 过滤。
10. 审计详情显示分数组件和 degrade_reason。
11. `Match Quality` 可按 strategy_id、match_source、bucket 观察。
12. 求职者/招聘方页面只展示受控解释，不改变默认排序。

- 降级结果没有 degrade_reason。

## 12. 残余风险

| 风险 | 等级 | 处理 |
| --- | --- | --- |
| 当前管理 API/UI 不能正式激活、发布或回滚智能策略 | P2 | 增加发布检查、状态流转、审计和回滚流程 |
| 生产级外部向量服务尚未接入 | P2 | 保留 provider adapter、超时与降级路径；上线前补真实索引证据 |
| 规则实验 treatment 尚未绑定智能策略 | P2 | 完成契约、运行时 bucket 选择和实验审计 |
| 前端 build 存在 chunk-size warning | P3 | 拆分管理端资源和大页面 |
| demo/mock 或本地 provider 证据被误用为上线证据 | P2 | 评估报告保留 sample source；生产决策要求独立证据 |

## 13. 交付判定

当前原型对应的本地实现已经落地，可以用于开发环境和 demo 验收，但不能据此宣称生产上线完成。

进入生产发布前至少需要：

- 接入生产级外部向量 provider，并验证索引版本、超时、降级和审计。
- 建立智能策略激活、发布检查、回滚和权限治理。

### 14.4 发现的缺口

| ID | 等级 | 缺口 | 影响 | 建议处理 |
| --- | --- | --- | --- | --- |
| G003-01 | P2 | 原型定义了向量索引版本和不可用状态，但没有单独定义“向量索引健康/可用性检查”的页面或接口入口。 | 策略能否进入 testing 需要依赖后端判断，前端只能显示结果。 | 在 BE-P4-04 或 BE-P4-02 中返回 `vector_readiness` 摘要；P0 不单独做运维页。 |

| G003-03 | P3 | Match Quality 原型写了 Degrade Reason 过滤，但接口契约当前只列出 `strategy_id` 和 `match_source`，未明确 `degrade_reason` 是否作为 quality summary 查询参数。 | 质量页可先展示降级率，但按降级原因过滤可能需要契约补充。 | 在 BE-P4-08 明确是否支持 `degrade_reason` 过滤；若不支持，前端先只展示分布不提供过滤。 |
| G003-04 | P3 | 原型建议 `behavior_quality_score` 字段，但契约已说明 P0 默认 0，数据来源不足时避免引入偏差。 | 如果前端展示为真实行为质量分，可能误导用户。 | 前端在 P0 中显示为 disabled/0 或隐藏；待真实行为样本充足后再开放。 |

### 14.5 需要同步到后续实现计划的事项

1. 第一批实现仍从 BE-P4-01、BE-P4-02 开始；不要先做前端假页面。
