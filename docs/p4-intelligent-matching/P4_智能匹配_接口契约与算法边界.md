# P4 智能匹配接口契约与算法边界

## 1. 目标与边界

本文承接 `P4_智能匹配_MVP_PRD.md`，定义 P4 智能匹配 MVP 的接口契约、数据依赖图和算法/规则边界。本文是后续工程拆分的输入，不代表已经实现。

`硬约束`：

- P3 规则匹配、规则版本、实验、审计、发布治理和 R-P4-01 Match Quality 已完成，P4 不重做。
- 默认线上匹配仍走现有 `GET /api/v1/matches/jobs/{job_id}/me` 规则基线。
- 智能匹配只能通过显式策略、离线评估和灰度实验启用。
- 任一智能组件失败时必须降级到规则基线，并写入审计。
- P0 不做 LLM 实时评分、LLM 自动改规则、招聘者侧候选排序正式上线。

## 2. 当前可复用接口

| 现有接口 | 用途 | P4 复用方式 |
| --- | --- | --- |

## 3. 新增接口契约

### 3.1 智能策略列表


```json
  "page": 1,
  "page_size": 20
```

Response：

```json
{
  "items": [
    {
      "id": 1,
```

### 3.2 创建智能策略草案

```text
POST /api/v1/matches/intelligent/strategies
```

权限：`admin`。P0 不开放给 recruiter/seeker。

Request：

```json
{
  "name": "hybrid-default-v1",
  "description": "P4 MVP hybrid scoring strategy",
  "base_rule_config_id": 42,
  "vector_recall": {
    "enabled": true,
    "top_n": 100,
    "min_similarity": 0.62,
    "candidate_source": "job_resume_profile"
  },
  "hybrid_weights": {
    "rule_score": 0.7,
    "vector_score": 0.2,
    "profile_coverage_score": 0.1,
    "behavior_quality_score": 0
  },
  "fallback_policy": "rule_baseline"
}
```

Response：返回单个 strategy，与列表 item 字段一致。

校验：

- `base_rule_config_id` 必须存在且不能是 `archived`。
- 权重总和必须等于 1.0，允许 0.001 浮点误差。
- `top_n` 范围：`1..500`。
- `min_similarity` 范围：`0..1`。
- `fallback_policy` P0 仅允许 `rule_baseline`。

错误：

- `400`: 权重不合法、策略名重复、fallback_policy 不支持。
- `404`: base rule 不存在。
- `409`: 引用的规则状态不允许进入 testing。

审计：

- 写入 `match_rule_operation_audits` 或后续智能策略操作审计。
- action: `create_intelligent_strategy`
- resource_type: `intelligent_strategy`
- after_snapshot: request + normalized weights。

### 3.3 策略详情

```text
GET /api/v1/matches/intelligent/strategies/{strategy_id}
```

权限：`admin`。

BE-P4-02 当前后端最小闭环的详情响应与创建/列表 item 字段保持一致，返回 `id/name/description/status/base_rule_config_id/vector_recall/hybrid_weights/fallback_policy/created_by/updated_by/archived_at/created_at/updated_at`。

`base_rule`、`evaluations`、`experiments`、`operation_audits` 属于管理端聚合详情视图字段，不在 BE-P4-02 后端最小闭环中强制一次性返回；前端可先分别调用规则、评估、实验、审计接口聚合展示，后续再按 FE/BE 联调需要新增聚合详情响应。

错误：

- `404`: strategy 不存在。

审计：详情查询不写操作审计。

### 3.4 更新策略草案

```text
PATCH /api/v1/matches/intelligent/strategies/{strategy_id}
```

权限：`admin`。

规则：

- 仅 `draft` / `evaluating` 可编辑。
- `testing` / `active` / `archived` 不允许原地修改，只能复制为新草案。

Request：同创建接口的可选字段。

错误：

- `409`: 当前状态不可编辑。

审计：

- action: `update_intelligent_strategy`
- before_snapshot / after_snapshot 必须记录。

## 4. 现有接口扩展

### 4.1 求职者岗位匹配响应扩展

```text
GET /api/v1/matches/jobs/{job_id}/me
```

P0 不改变默认行为。仅命中智能实验 treatment 时，在现有 `JobMatchResponse` 基础上追加可选字段：

```json
{
  "match_source": "rule_baseline|hybrid",
  "intelligent_strategy_id": 1,
  "score_components": {
    "rule_score": 82.0,
    "vector_score": 76.5,
    "profile_coverage_score": 90.0,
    "hybrid_score": 81.1
  },
  "recall_source": "rule_only|vector_only|rule_and_vector",
  "degrade_reason": null
}
```

兼容要求：

- 老前端不读取这些字段也不能出错。
- `degrade_reason != null` 时，`match_source` 必须回到 `rule_baseline` 或标记 `hybrid_degraded`。

### 4.2 规则实验创建扩展

```text
POST /api/v1/matches/rule-experiments
```

新增可选字段：

```json
{
  "treatment_strategy_type": "rule_config|intelligent_strategy",
  "treatment_intelligent_strategy_id": 1
}
```

约束：

- P0 control 必须是现有规则配置。
- treatment 可为智能策略，但 strategy 必须是 `testing`。
- 一个 `scope + template_key` 仍最多一个 running experiment。

当前实现说明（2026-07-10）：规则实验创建接口尚未接收 `treatment_strategy_type` 或 `treatment_intelligent_strategy_id`。运行时当前直接选择数据库中的 `active` 智能策略。本节描述的是待实现的目标契约。

## 5. 数据依赖图

| 数据域 | 当前来源 | P4 使用方式 | 风险/约束 |

| match audits | `match_rule_match_audits` | baseline/hybrid 对比事实源 | 智能字段只扩展不覆盖规则字段 |

| rule experiments | `match_rule_experiments` | 灰度 control/treatment | running 冲突继续阻断 |
| operation audits | `match_rule_operation_audits` | 策略、评估、实验绑定操作记录 | 后续可拆独立智能策略审计表 |
| vector index metadata | 新增或外部索引元数据 | 判断索引版本、覆盖率、降级原因 | P0 不要求完整特征平台 |

## 6. 算法/规则边界

### 6.1 规则基线

- 规则基线是安全底座，任何智能策略都不能绕过。
- 规则分必须作为 `hybrid_score` 的主分量。
- 规则解释、维度快照、rule_config_id、experiment_bucket 必须继续写入审计。

### 6.2 可选向量召回

- 向量召回是候选补充，不是最终决策。
- 输入限定为岗位文本、标准职位、标签、求职意向、结构化简历画像。
- 不把原始简历敏感文本直接返回给前端。
- 向量索引缺失、版本过期、服务超时、相似度低于阈值时降级。

### 6.3 可选 LLM 解释

- P0 不启用 LLM 实时解释。
- P1 若启用，只能基于审计字段生成可追溯自然语言解释。
- LLM 输出不得成为分数来源，不得自动修改规则，不得自动发布。

### 6.4 混合评分

P0 推荐公式：

```text
hybrid_score =
  rule_score * rule_weight +
  vector_score * vector_weight +
  profile_coverage_score * profile_coverage_weight +
  behavior_quality_score * behavior_quality_weight
```

P0 默认：

```json
{
  "rule_score": 0.7,
  "vector_score": 0.2,
  "profile_coverage_score": 0.1,
  "behavior_quality_score": 0
}
```

约束：

- 权重必须显式存储并进入审计。
- `behavior_quality_score` P0 默认 0，避免行为反馈不足时引入偏差。
- 低规则分候选不得仅因语义分高直接高排；需设置规则分安全阈值。


#### 6.4.1 与三维评分模型的兼容关系

P4 的 `rule_score/vector_score/profile_coverage_score/behavior_quality_score` 是策略层抽象，不应替代既有三维人岗匹配模型。第一版实现必须保留三维主分：

```text
base_match_score =
  semantic_score * 0.50 +
  tag_score * 0.30 +
  keyword_score * 0.20
```

字段映射：

| 既有三维字段 | P4 字段 | 含义 |
| --- | --- | --- |
| `semantic_score` / `embedding_score` | `vector_score` | JD 与简历/人才画像的语义相似度 |
| `tag_score` | `rule_score` 的组成部分 | 岗位标签与人才标签匹配度 |
| `keyword_score` | `rule_score` 的组成部分 | JD 关键词与简历关键词匹配度 |
| `profile_coverage_score` | 独立辅助项 | 画像完整度/可信度，不代表匹配好坏 |
| `behavior_quality_score` | 独立辅助项 | 真实业务行为反馈，P0 默认 0 |

推荐融合公式：

```text
rule_score = tag_score * 0.60 + keyword_score * 0.40

final_hybrid_score =
  base_match_score * 0.85 +
  profile_coverage_score * 0.05 +
  behavior_quality_score * 0.10
```

P0 执行约束：

- `behavior_quality_score = 0`，只保留字段和权重配置，避免无真实行为样本时引入偏差。
- `profile_coverage_score` 最高只作为 5%~10% 的可信度修正项，不得替代匹配分。
- 强约束字段（城市、学历、年限、薪资、必要技能、岗位有效状态）先过滤或强降权，不得被高语义分覆盖。
- 审计必须同时记录三维分、画像覆盖分、行为质量分、最终分和权重版本。

行为质量分可用信号：招聘方查看详情、收藏、发起沟通、邀约面试、标记合适/不合适、录用；求职者查看岗位、收藏、投递、回复沟通、接受面试、入职反馈。进入生产前必须经过样本量阈值和偏差审查。

### 6.5 Fallback

降级优先级：

1. 智能策略配置非法：不进入 treatment。
2. 向量召回失败：回退规则 baseline。
3. 画像不完整：降低语义权重或回退规则 baseline。
4. 审计写入失败：返回匹配结果前必须确保规则 baseline 可审计；不能产生不可追溯智能结果。

### 6.6 Observability

必须可观察：

- `strategy_id`
- `match_source`
- `vector_index_version`
- `degrade_reason`
- `score_components`
- `vector_recall_coverage`
- `degrade_rate`
- baseline vs hybrid quality delta

### 6.7 Governance

- 策略草案必须先跑离线评估。
- 样本来源为 `seeded_demo` / `mock_only` 的评估不能进入上线灰度。
- 灰度必须复用 experiment lifecycle。
- 发布必须复用 release-check / operation audit 思路。
- 任何自动扩量、自动回滚、自动权重学习都不属于 P0。
