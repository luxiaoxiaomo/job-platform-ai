# 多 AI 协作约定（Claude × Codex）

> 背景：2026-06-15 发现看板表格被并发编辑覆盖——Claude 标 Done 的任务被改回 Todo、R-P1-06 整行消失。本约定用于避免此类冲突。

---

## 一、核心原则

1. **看板表格是唯一事实源，但只能"小步、定向"地改，不能整段重写。**
2. **每个任务行只有它的 Owner 能改状态**，对方不碰。
3. **改看板前必须先 fetch 最新版**，基于最新内容做 str_replace，不要基于记忆里的旧版本改。
4. **代码以仓库为准，看板以最新 revision 为准**；两者不一致时，先同步看板，不要回滚代码。

---

## 二、看板表格编辑规则（重点）

### 2.1 状态列只改自己 Owner 的行

| Owner | 可改的行 |
|-------|---------|
| Codex | Owner=Codex 的行 |
| Claude | Owner=Claude 的行 |
| Both | 各自只改自己负责的那一侧，状态用 `Review`，由双方确认后才置 `Done` |

不要去改对方 Owner 行的状态。

### 2.2 改状态用"精确定向替换"，禁止整表重写

✅ 正确做法（只替换一个单元格的状态值）：
```
str_replace
  pattern:  画像页去掉误导性 mock AI 文案 | Claude | Todo
  content:  画像页去掉误导性 mock AI 文案 | Claude | Done
```
pattern 里带上**任务描述 + Owner + 旧状态**，保证唯一匹配，且只动一个值。

❌ 禁止做法：
- 用 `overwrite` 重写整个文档
- 一次 str_replace 替换包含多行的大段表格
- 凭记忆拼一整行去替换（容易把别人改的内容覆盖掉）

### 2.3 改之前先 fetch

每次要改看板，先：
```
docs +fetch --api-version v2 --doc <id> --doc-format markdown
```
看清当前这行的**真实文案和状态**，再基于真实文案做 str_replace。
（之前的覆盖就是因为基于旧版本 str_replace，把对方的更新冲掉了。）

### 2.4 新增任务行

- 新增任务行：用 `str_replace` 把"表格最后一行"替换成"最后一行 + 新行"，不要 append 到表格外。
- 新增行要写全 8 列：ID / 阶段 / 任务 / Owner / 状态 / 文件边界 / 依赖 / 验收。
- 新增前先 fetch，确认 ID 不重复。

---

## 三、状态流转定义

| 状态 | 含义 | 谁来置 |
|------|------|--------|
| `Todo` | 未开始 | 创建者 |
| `In Progress` | 进行中，Owner 已锁定对应文件 | Owner |
| `Blocked` | 被依赖/bug/接口阻塞，需注明阻塞项 | Owner |
| `Review` | Owner 自测完成，等对方或用户验收 | Owner |
| `Done` | 已验收通过 | 验收方（Both 任务需双方都确认）|

- **单 Owner 任务**：Owner 自测通过可直接置 `Done`。
- **Both 任务**（如联调）：各自完成自己一侧置 `Review`，双方都 Review 后才有人置 `Done`。

---

## 四、文件边界（防止同时改同一文件）

| 区域 | 默认 Owner |
|------|-----------|
| `backend/**`（含 alembic 迁移、models、schemas、service、api） | Codex |
| `frontend/wechat-prototype/src/seeker/**`、前端页面/交互 | Claude |
| `frontend/wechat-prototype/src/services/*.js`（接口封装层） | 谁联调谁改，但**改前在看板说明**，Codex 只定义返回结构 |
| `docs/简历解析底座技术设计.md`（最终技术方案） | Codex 维护，Claude 只提建议 |
| Alembic migration 文件 | **永远只由 Codex 创建**（避免 revision 冲突）|

- 必须改对方文件时：先在看板"同步区"写明【要改哪个文件 + 原因】，等对方知晓再动。

---

## 五、每次干完活，在看板"同步区"追加一条（只 append，不改表格正文）

格式固定：
```text
Owner: <Codex/Claude>
Doing: <任务ID + 简述>
Changed files: <改动的文件列表>
Blocked by: <阻塞项，无则写"无">
Next: <下一步>
```

同步区追加用 `append`（加到文档末尾），**不要动上面的任务表格**。这样同步记录和表格状态分离，互不覆盖。

---

## 六、发现对方负责的问题怎么办

不直接改对方代码。改为：
1. 在看板新增一行 bug/task，Owner 指给对方；
2. 在同步区写清楚：现象、复现、影响、归属文件、修复建议；
3. 自己的依赖任务置 `Blocked`，注明被哪个 bug 阻塞。

（参考 R-P1-BUG01 的处理方式，那次流程是对的。）

---

## 七、冲突发生后的恢复流程

如果又出现表格被覆盖/行丢失：
1. 谁先发现，谁 fetch 最新版，**只在同步区**记录"表格异常"，不要急着改表格；
2. 由一方（建议 Codex，因为表格行多在后端侧）统一修复表格一次；
3. 修复时逐行核对状态，参考双方最近的同步区记录还原真实状态。

## 九、Codex 补充约定

1. 看板是任务状态的事实源；代码实现以 Git 仓库为准；设计决策以 `docs/` 下的技术设计文档为准。三者不一致时，先同步状态，不回滚代码。
2. 复杂 bug 不直接塞进任务表格。先写到同步区或 Bug 区，确认 Owner 和修复范围后，再由一个人整理成表格任务行。
3. 新增任务必须有明确 ID。不要写“待 Codex 处理某问题”这种自由文本，统一写成 `R-xxx` 或 `BUG-xxx`，方便另一台机器接手。
