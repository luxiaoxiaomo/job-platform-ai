# 项目审核报告：空岗信息发布对接平台

审查日期：2026-06-05  
审查范围：`backend/job-platform`、`frontend/wechat-prototype`、`frontend/react-vite-prototype`、根目录与关键项目文档  
审查方式：静态代码阅读、配置检查、构建验证、测试可用性检查

## 结论摘要

当前项目已经具备清晰的前后端雏形：后端采用 FastAPI，前端包含两个 Vite 原型项目。两个前端项目可以完成生产构建。

主要风险集中在后端用户认证与隐私链路：手机号使用 Fernet 密文直接做唯一性和登录查询，这在设计上不可行，会导致重复注册检查失效、登录查不到用户。其次，用户资料接口存在横向读取他人手机号的风险，数据库迁移和测试也尚未形成可交付闭环。

## 高风险问题

### H-01 手机号加密查询设计不可用

影响文件：

- `backend/job-platform/app/modules/user/service.py:43`
- `backend/job-platform/app/modules/user/service.py:79`
- `backend/job-platform/app/modules/user/repository.py:61`
- `backend/job-platform/app/modules/user/models.py:17`

问题说明：

当前注册和登录都通过 `encryptor.encrypt(data.phone)` 得到 `phone_encrypted`，再用密文查询数据库。Fernet 是非确定性加密，同一个手机号每次加密会生成不同密文。因此：

- 注册时重复手机号检查大概率查不到已有用户。
- 登录时无法通过手机号再次生成相同密文，也就查不到已注册用户。
- `phone_encrypted` 上的唯一约束不能实现“手机号唯一”。

影响：

这是认证主链路的阻断性缺陷。用户注册、登录、手机号唯一性都无法可靠工作。

建议：

增加一个不可逆但可稳定查询的字段，例如：

- `phone_hash = HMAC-SHA256(hash_secret, normalized_phone)`
- 对 `phone_hash` 建唯一索引。
- 注册、登录、查重使用 `phone_hash`。
- `phone_encrypted` 仅用于需要展示手机号时解密。

迁移时需要补充 `phone_hash` 字段，并为已有数据生成对应 hash。

### H-02 加密器初始化失败后运行时才暴露 500

影响文件：

- `backend/job-platform/app/utils/encryption.py:59`
- `backend/job-platform/app/modules/user/service.py:43`
- `backend/job-platform/app/api/v1/users.py:31`

问题说明：

`FieldEncryptor` 初始化失败时，代码只是发出 warning 并设置 `encryptor = None`。但业务代码没有判空，直接调用 `encryptor.encrypt()` 和 `encryptor.decrypt()`。

影响：

当 `ENCRYPTION_KEY` 缺失、为空、格式错误，或部署环境误配时，服务仍可能启动，但注册、登录、用户信息接口会在请求时抛出 500。这类错误应该在启动阶段失败，而不是进入运行期。

建议：

- 加密器初始化失败时直接阻止应用启动。
- 在配置层校验生产环境不能使用空值或占位密钥。
- 增加启动配置测试，覆盖 `ENCRYPTION_KEY` 缺失和非法格式。

### H-03 任意登录用户可读取其他用户手机号

影响文件：

- `backend/job-platform/app/api/v1/users.py:67`
- `backend/job-platform/app/api/v1/users.py:82`

问题说明：

`GET /api/v1/users/{user_id}` 只要求登录，不校验当前用户是否有权访问目标用户。响应中会解密并返回目标用户手机号。

影响：

任意登录用户可以枚举 `user_id` 读取其他用户手机号，属于横向权限和隐私泄露问题。

建议：

- 完整用户资料仅允许本人或管理员访问。
- 招聘/求职场景如需查看对方信息，应走业务授权关系，例如已投递、已沟通、已面试。
- 普通公开资料接口不要返回手机号，或返回脱敏手机号。

## 中风险问题

### M-01 数据库迁移缺失

影响文件：

- `backend/job-platform/README.md:50`
- `backend/job-platform/alembic/versions`

问题说明：

README 要求执行 `poetry run alembic upgrade head` 初始化数据库，但 `alembic/versions` 目录为空，没有首个建表 migration。

影响：

新环境启动后不会创建 `users` 表。注册、登录等接口即使逻辑修复，也会因为表不存在失败。

建议：

- 生成首个 Alembic migration，至少包含 `users` 表、枚举类型、索引。
- 将 migration 纳入交付检查。
- 在 CI 中加入 `alembic upgrade head` 验证。

### M-02 验证码接口缺少频率限制

影响文件：

- `backend/job-platform/app/api/v1/auth.py:89`
- `backend/job-platform/app/api/v1/auth.py:121`
- `backend/job-platform/app/core/config.py:14`

问题说明：

`send-verification-code` 没有手机号/IP 维度的频率限制。当前开发环境会直接返回验证码，后续接入真实短信服务后会带来刷短信和撞库辅助风险。

影响：

可能造成短信成本失控，也可能被用于批量探测手机号注册状态或辅助攻击认证流程。

建议：

- 对手机号和 IP 增加限流，例如每分钟、每小时、每日上限。
- 验证码返回只允许显式测试开关，不应仅依赖 `ENV=dev`。
- 记录验证码发送审计日志。

### M-03 后端测试为空

影响路径：

- `backend/job-platform/tests`
- `backend/job-platform/pyproject.toml:29`

问题说明：

项目已经配置 pytest、pytest-asyncio、pytest-cov，但测试目录只有空 `__init__.py`，没有实际测试用例。

影响：

认证、权限、加密、数据库迁移这类高风险逻辑没有自动化防线。后续迭代容易反复引入同类问题。

建议：

优先补充以下测试：

- 注册成功与重复手机号注册。
- 登录成功与错误密码。
- Fernet 加密不用于查询，`phone_hash` 可稳定查询。
- `/users/{user_id}` 仅本人/管理员可访问完整资料。
- 缺少或非法 `ENCRYPTION_KEY` 时应用启动失败。

## 低风险与工程质量问题

### L-01 Web 原型构建包偏大

影响项目：

- `frontend/react-vite-prototype`

验证结果：

`npm.cmd run build` 成功，但 Vite 提示主 chunk 约 `1,578.61 kB`，超过默认 500 kB 告警阈值。

影响：

作为原型问题不大；如果后续转为正式 Web 应用，会影响首屏加载和缓存效率。

建议：

- 对路由页面使用 `React.lazy()` 和动态导入。
- 将 Ant Design、Recharts 等大依赖拆分为 vendor chunk。
- 对管理端和移动端原型拆分入口。

### L-02 根 README 在默认 PowerShell 读取时易出现乱码

影响文件：

- `README.md`
- `backend/job-platform/README.md`

问题说明：

文件本身是 UTF-8，使用 `Get-Content -Encoding UTF8` 可正常读取；但默认 PowerShell 编码读取时会显示乱码。

影响：

不影响程序运行，但会降低 Windows 环境下的文档可读性。

建议：

- 保持文件 UTF-8。
- 如团队主要使用 Windows PowerShell，文档中注明使用 UTF-8 编码查看。
- 可考虑统一 `.editorconfig`，明确 `charset = utf-8`。

## 建议整改顺序

1. 修复手机号查询设计：新增 `phone_hash`，迁移唯一索引，注册/登录改用 hash 查询。
2. 修复隐私权限：限制 `/api/v1/users/{user_id}`，拆分完整资料和公开资料。
3. 强化配置启动校验：缺失或非法 `ENCRYPTION_KEY`、JWT 密钥占位值时直接启动失败。
4. 补齐首个 Alembic migration，并用空库执行验证。
5. 增加后端认证与权限测试。
6. 为验证码接口补限流和测试模式开关。
7. 前端正式化前再做代码分割和包体积优化。

## 可交付状态判断

前端原型可以作为演示版本继续使用。后端当前不建议进入联调或试运行，原因是认证主链路存在阻断性缺陷，且缺少数据库迁移和测试保障。建议先完成高风险项整改，再进入接口联调。
